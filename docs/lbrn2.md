# LBRN2 projects

`phoenix-laser` reads `.lbrn2` project files (and `.lbrn` ones, the older format, see below), the project format of a laser program of another maker (its names are trademarks of their owners). `cut`, `vector`, `layers` and `convert` take one in place of an SVG or a DXF, and the window opens it like a drawing. There is no published specification of the format: the reader was written from the behaviour of real files, and what it does with each part is below. Nothing is copied from another program.

## What is read

The file is XML. The root is a `LightBurnProject` element; its attributes `AppVersion`, `DeviceName`, `FormatVersion`, `MirrorX` and `MirrorY` are kept and shown, nothing is done with them.

| Part | What the reader does |
|---|---|
| `CutSetting` and `CutSetting_Img` (a layer) | the `type` (`Cut`, `Scan`, `Image`; any other word is kept as written), and one child per value with a `Value` attribute. Read: `index`, `name`, `maxPower` (percent), `minPower`, `speed` (mm/s), `numPasses`, `interval` (mm between the lines of a fill), `priority` (the order of the layers) and `doOutput` (a layer that is not sent to the laser is skipped). Every value is kept as written. |
| `Shape` with `CutIndex` | the layer of the shape is the layer with that number (its name, or `C` and the number with two digits when it has none). |
| `XForm` | six numbers `a b c d e f`: `x' = a x + c y + e`, `y' = b x + d y + f`, from the space of the shape to the space of its parent. A shape whose transform is not six numbers has no place and is left out. |
| `Rect` | `W` and `H`, centred on its origin; `Cr` is a corner radius (it was zero in every real example, so the rounded corner is the part least checked). |
| `Path` | `VertList`: vertices written `V x y`, each followed by the optional handles `c0x c0y c1x c1y`; a handle given with only its x (the value 1) is no handle. `PrimList`: `L a b` is a line from vertex `a` to vertex `b`, `B a b` a cubic Bezier that leaves `a` through its `c0` and arrives at `b` through its `c1`; the word `LineClosed` is a closed polygon through all the vertices. A new outline starts where a piece does not begin at the end of the one before; an outline that returns to its first vertex is closed. |
| `VertID`, `PrimID` | a path may leave its lists out when an earlier path wrote them under the same number; a number nobody wrote skips the path with a note. |
| `Group` with `Children` | the matrix of the child acts first, the matrix of the group second, at any depth. |
| `Text` | drawn from its `BackupPath`, the outline of the letters, whose `XForm` is the one that places the text (it is applied once). A text that has only its letters (`Str` and the height `H`, as the older format writes it) is drawn with the stroke font of the program in capitals, placed by `Ah` (across: 0 left, 1 centre, 2 right) and `Av` (up: 0 top, 1 middle, 2 bottom); that is a guess at the shape and the place of the text, said in a note, and a character that the font has not is left blank. A text with no letters or with a height that the font refuses is left out. |
| `Bitmap` | a picture: `W` and `H` are its size, centred on its origin, and `Data` is the picture as base64 text (a PNG in every real example; a PGM is read too). It is decoded within the limits `max_bitmap_bytes`, `max_bitmap_pixels` and `max_bitmaps` of `[limits]`, turned and mirrored as its `XForm` places it (a flip and a quarter turn; any other turn is refused) and kept for engraving, not drawn in the cut. See below. |
| `Ellipse`, `Polygon` | **prototype, no real project had one.** An `Ellipse` has the radii `Rx` and `Ry` (or one radius `R`), centred on its origin; a `Polygon` has `N` sides (3 to 1000) on the ellipse of `Rx` and `Ry`, with a vertex pointing up. Both are written from the names of the attributes alone, with projects written for the tests, and are counted in the notes when they have no size or no number of sides. An array of copies is not a shape of its own in what was seen: its copies are groups, which the reader already follows. |
| `tabsEnabled`, `tabCount`, `tabSize` (a layer) | **prototype.** For a layer that cuts, `tabsEnabled` on gives the layer that many tabs (`tabCount`, 0 to 100) as long as `tabSize` mm (the width of the program when the layer gives none); `tabsUseSpacing` and `manualTabs` are not used. They are hints of the table of layers, like the rest of the layer. |
| `VariableText` | the counter of the project: `Start`, `End`, `Current`, `Increment` and `AutoAdvance`, each with a `Value`. `phoenix-laser text --counter-project PROJECT.lbrn2` makes the series from `Current` to `End`. The text of the project is not changed, and no variable text of a shape (a text that names a column) is read: the series is made by `text` with its own places, see `docs/vector-settings.md`. |

The curves are cut into straight pieces that are never farther than `tolerance_mm` of `[read]` from the curve. The limits of `[limits]` hold: the size of the file, the depth of the elements, their number, the shapes, the points and the coordinates; a declared entity is an error.

The y axis of the file is taken as the one of an SVG (it points down), so the drawing is turned over when it is cut. **That was never confirmed with a real part**: if a cut comes out as a mirror image, this is where to look. The setting `lbrn2_flip_y` of `[read]` (on by default, which is what was always done) chooses the direction: `off` takes the y axis of the file as pointing up like the one of the machine, and the drawing and the pictures are not turned over. Every reading of a project that holds a drawing or a picture says in its notes which direction it used and that it is not confirmed, so the note is in the report before a job and in the window whichever way the setting is.

## The older format (`.lbrn`)

A project of the older format has the same root and the same layers and shapes, and writes a path another way: one `V` element for each vertex (`<V vx="0" vy="0"/>`, with `c0x c0y c1x c1y` when it has handles) and one `P` element for each piece (`<P T="L" p0="0" p1="1"/>`, `T="B"` for a curve) instead of the two lists of text. Both ways are read, and every command and the window take the extension `.lbrn` as they take `.lbrn2`. The older format was measured on a handful of real projects (their shapes, layers and texts were read; nothing was cut), kept outside of this repository like the others. The layers of a project reach `cut`, `vector` and `layers` with `--project-layers`.

## Pictures

A `Bitmap` is decoded (base64, then the PNG) and turned as its transform places it, so that the first row of the picture is the top as it will be seen on the machine. `phoenix-laser engrave PROJECT.lbrn2 OUT.nc` engraves it by dots like any other picture, with every option of `engrave`: `--picture N` takes the Nth picture (the first by default), the width of the project is used when `--width-mm` is left out, the aspect is the one the project gives, and the power and the speed of the layer of the picture are used when the command line gives none (a power or a speed over the limit is refused, never lowered, and the command says that the values come from the layer). What is refused is told with a stable code in the notes: `PHOENIX-LASER-LBRN2-BITMAP-SIZE` (the text of the picture is longer than `max_bitmap_bytes`), `-PIXELS` (more pixels than `max_bitmap_pixels`, read from the header of the PNG before anything is unpacked), `-COUNT` (more pictures than `max_bitmaps`), `-FORMAT` (a JPEG or any other format: only a PNG and a PGM are decoded, and there is no decoder of other formats in the program), `-DATA` (the text is not base64 or the picture is damaged) and `-ROTATED` (a turn that is not a quarter turn). The tone, dithering and the rest of `engrave` are applied to the picture; the picture options of the project (gamma, contrast, brightness, the cropping and the dither of the layer) are not read.

## What the layers give the table

A layer of the project becomes a row of the table of layers with: the mode (`cut` for a `Cut`, `engrave` for the rest, `skip` for a layer that is not sent to the laser), the power, the speed in mm/min (the file has mm/s, so the value is multiplied by 60), the passes, the distance between the lines of a fill and the order. They are hints: the limits of the machine hold over them when the work is made (a power over the limit is an error that names the layer, never lowered), a layer that the settings file names keeps what the settings file says, and the window notes that the values are the project's and have to be checked for the machine.

## What is left out

Said in the notes of the drawing and counted:

* a picture that is over a limit, in a format that is not read, damaged or turned by something other than a quarter turn (with its code, see above);
* a shape of a type that is not read (any `Type` other than `Rect`, `Path`, `Group`, `Text`, `Bitmap`, `Ellipse` and `Polygon`);
* a text with no outline and no letters, a text that the stroke font refuses (nothing it can draw, or a height over its limit);
* a path whose lists are missing or damaged, a rectangle, ellipse or picture without a size, and a polygon without a number of sides from 3 to 1000.

The rest of the file (the preview picture, the text of the variable text of a shape, the options of the optimiser, the settings of picture layers, the notes) is not used.

## How it was measured

The reader was run over twelve real projects made by a laser maker, of versions 1.5 to 2.0 of the program that wrote them, from 40 kB to 10 MB, kept outside of this repository and read only (they are not copied here and no test uses them; the tests use projects written for them with the same structure). All twelve are read (with the newest reader, in a build for debugging: in 170 ms or less each, except the one that holds a picture, 1.7 s); 4,300 paths, 47 groups, two rectangles and one text are drawn; the one picture, in the largest file, is a PNG of 4096 x 4096 pixels: it is decoded and engraved by dots (a dry run of `engrave` at dots of 0.5 mm takes about 8 s in a build for debugging), and the default of `max_bitmap_pixels` (20 million) was chosen so that it fits. Tab settings appear in 25 layers and are switched on in one of them only (a cut with two tabs of 0.2 mm); every project has the variable text block with the values 0, 999, 0 and 1, and none has an ellipse, a polygon or a JPEG. Two details were confirmed against the files themselves: the speeds and the powers of the layers agree with the values the maker wrote in the notes that come with them (the speed is in mm/s), and the drawing of the plate with a text measures exactly the size of its rectangle when the transform of the text is applied once. The direction of the handles (`c0` leaves the first vertex, `c1` arrives at the second) holds for 98 % of the 16,600 Bezier pieces that give both handles (the handle points towards the other end of the piece); in the rest it points the other way, as it does at a cusp.

`examples/lbrn2_survey.rs` is the tool: `cargo run --release --example lbrn2_survey -- FOLDER [--out REPORT.txt]` reads every `.lbrn2` file under a folder and says which are read, which are not and why, what each holds, and which elements and attributes the files have that the reader does not use. The exit code is 2 when a file is not read. It writes nothing but its report.

## Not tried

No program made from a project has been cut or engraved on a machine. Not confirmed: the orientation of the y axis (see `lbrn2_flip_y`), the corner radius of a rectangle, the ellipse, the polygon and the tabs (written from the names of the attributes, no real project had them in use), and the engraving of a picture (twelve real projects were measured and only one held a picture, a PNG; the engraving is tested on pictures made for the tests). A JPEG inside a project is not read.

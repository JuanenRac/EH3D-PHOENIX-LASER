# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **QR code in the window:** a new mode has a box for the data, a choice of the level of error correction and one box for each key of `[qr]` (the side of a module, the distance between the lines, the power, the speed, the passes, the most bytes, the largest version and side, and the most burning moves), a file of settings fills them, and the symbol is worked out with the same function as `phoenix-laser qr` from the origin of the machine, so data that does not fit, a symbol over a limit, a power or a speed over the limit of the machine or work outside of the bed is refused with the box or the reason named in the status line; it is written as `qr.nc` with the usual header.
- **QR code:** `phoenix-laser qr OUT.nc --text DATA` burns data as a QR code of the program's own: versions 1 to 4 (21 to 33 modules a side) in byte mode, the four levels of error correction (`--ecc L|M|Q|H`, Reed-Solomon) and the mask with the lowest penalty, filling each dark module with lines (`--module-mm`, `--line-mm`); `--print` shows the symbol as text. The new `[qr]` section holds the usual values (`module_mm`, `line_mm`, `power_percent`, `speed_mm_min`, `passes`, `max_bytes`, `max_version`, `ecc`, `max_size_mm`, `max_lines`). Data over `max_bytes`, a version over `max_version`, a symbol larger than `max_size_mm`, a fill of more than `max_lines` moves, a power or a speed over the limit or work outside of the bed is refused, never cut down or shrunk, and the data is never written into a comment of the program.
- **Text in the window:** a new mode has a box for the words and one box for each key of `[text]` (the height of a capital, the tallest letter, the gaps between letters and rows, the power, the speed, the passes and the most characters), a file of settings fills them, and the text is worked out with the same function as `phoenix-laser text` from the origin of the machine, so a letter that the font has not, a text over a limit, a power or a speed over the limit of the machine or work outside of the bed is refused with the box or the reason named in the status line; it is written as `text.nc` with the usual header.
- **Text in the security notes and in the architecture picture:** `SECURITY.md` now says what each command writes (and that it is never written over a file it is made from), the security table of the README in the eight languages has a row for the limits of the text, and the architecture picture and its description show the text command and the engraving of a picture as one box, with no stale test count.
- **Cross hatch in the window and in the library of materials:** the table of layers of the window has a box for the cross hatch of each layer, a file of settings fills it from `hatch_cross`, and a material of the library can ask for it with `hatch_cross = on` (or turn it off with `off`; a material that says nothing leaves it as it is) like it does for the angle and the spacing of the hatch. The example library asks for it on the engraving of birch.
- **The check can be tied to the program that was authorised:** `phoenix-laser verify PROGRAM.nc --expect-sha256 HASH` fails the program (exit code 1, a problem in the text and in the JSON report) when the SHA-256 of the file is not the 64 hex digits that were given, in any case, and says the one it has, so a program that was changed after it was looked at is not run by mistake. A value that is not 64 hex digits is refused before the program is read.
- **Cross hatch:** a layer that is engraved can be filled twice, with `hatch_cross = on` in its settings or `--cross` (and `--no-cross`) in `vector` and `trace`: after the lines at `hatch_angle` the shapes get a second set at right angles to them, with the same spacing, in every pass. The limit of lines (`max_lines` of `[hatch]`) holds over each set, the energy of a square millimetre that the list of layers gives is doubled, and the burnt length, the preview and the check of the program count both sets. Off by default, so no program changes unless it is asked for.
- **Text with a font of strokes:** `phoenix-laser text OUT.nc --text TEXT` burns a name, a serial number or a mark with a font of the program's own (capitals, figures, space and `. , - + / : ! ? ( ) = _ '`, each a few strokes on a lattice 4 wide and 6 high; lower case is burnt as capitals and a new line starts a row), so no picture and no font file are needed. The height of a capital, the gaps between letters and rows, the power, the speed and the passes are the keys of the new `[text]` section of the settings file (and the options `--height-mm`, `--spacing`, `--line-spacing`, `--power`, `--feed` and `--passes`), at `--origin X,Y`. A character the font has not, a text of more than `max_chars` characters (200 by default), a height over `max_height_mm` (100 mm), a power or a speed over the limit of the machine, or a text that would go outside of the bed is refused and nothing is written; the text is never written into a comment of the program, so a parenthesis in it cannot let the rest of the line through.
- **The check of a program in the window:** a G-code program that is opened to be seen is now also checked by `phoenix-laser verify`, with the limits of the window and the bed of the settings file: the side panel says whether it passes (with the start of its SHA-256, in green) or what is wrong (in red). A new box holds the overscan that is allowed past the bed with the laser off, the same as `overscan_mm` of `[verify]` and `--overscan-mm` (0 by default, from 0 to 100; a value outside of that is refused and the box is named), and a settings file fills it. A program that burns outside of the bed fails whatever the box says. The words are in the eight languages.
- **The grid from a material in the window:** the calibration mode lists the materials of the library and, with one picked, makes the grid with the same ladder as `phoenix-laser calibrate --material` (the power and the speed of the material in the middle, held between the lowest values and the limits, a material over a limit refused). The boxes are the steps, the spread, the lowest power and the lowest feed, and a switch burns the figures next to the squares with the height of its box; a settings file fills all of them from `[calibrate]`. With no material picked it is the grid of the two lists, as before. The words are in the eight languages.
- **The figures come by default with a material, and the lowest power and feed of the ladder are settings:** `phoenix-laser calibrate --material` now burns the power of each column and the feed of each row next to the squares without being asked (`--no-labels` takes them away; a grid made from `--powers` and `--feeds` is the same as ever and has figures only with `--labels`). The two lowest values that the ladder is held at, 1 % of power and 10 mm/min, are now the keys `min_power_percent` and `min_feed_mm_min` of `[calibrate]` with those values by default (more than 0 up to 100, and more than 0 up to 30000), and the example file, the help and the docs say the same.

## [0.0.9] - Trace and machine profiles in the window, uses in SVG, an overscan limit in verify, a test grid from the materials and a fuller verify report

- **The outline of a picture in the window:** a new mode follows the outline of the picture that is open with the same function as `phoenix-laser trace` and cuts it, or fills the shapes with lines, as a layer called `trace`. The boxes are the threshold, the simplification and the smallest piece (they start from `[trace]`), with a switch for a picture whose light part is the ink and another to fill instead of cut; the power and the speed are the ones of the laser boxes and obey the limits of power and of speed, and the limits of the picture (`max_pixels`, `max_contours`, `max_segments`) are the ones of the settings file, so a picture that is too detailed is an error and not a slow program. The frame of the window works from the outline too, and the words are in the eight languages.
- **A machine profile can be chosen in the window:** when the settings file describes machines with `[profile NAME]` sections, a new group of the side panel lists them and the one that is picked becomes the machine, like `--profile NAME` does: the boxes of the full-power value and of the limits of power and of speed take its values, the bed of the profile is the one the frame and the preview check, and what a profile leaves out comes from `[machine]` and never from the profile that was picked before. The limits still refuse a power or a speed over them, a profile that the file does not have changes nothing and the error lists the ones it has, and choosing a profile makes the work stale and takes back the answer to the question of the frame. The words are in the eight languages.
- **A `use` in an SVG brings in the element it refers to:** `<use href="#id">` (or `xlink:href`) of a shape, a group or a `symbol` of the same file is read again where the `use` is, moved by its `x` and `y`, under its `transform` and giving it its paint and layer; the element can be in the `defs` or come after the `use`, a `use` can bring in a group that has other `use`, and a `symbol` with a `viewBox` is fitted to the `width` and `height` of the `use`. What a `use` brings in counts against `max_nodes`, `max_depth`, `max_shapes` and `max_points` like any other element, so a file that multiplies itself is an error and not a slow program, and a `use` that leads back to an element that is being expanded is an error that says it is a circular reference. A `use` of another file or an address, with no `href` or of an id the file does not have is still skipped with a note, and nothing is fetched.
- **The overscan of another program can be allowed in `verify`, as far as the person says:** work outside the bed is a failure, and `--overscan-mm MM` (or `overscan_mm` in the new `[verify]` section of the settings file, 0 by default, from 0 to 100; the option wins) lets the head go that far past the bed with the laser off, as the overscan of the hatch lines of another program does. The program then passes with a note that says how far the head goes. A move that burns outside the bed fails whatever the allowance is, a program that goes past the bed by more than the allowance fails with a problem that says both numbers, and the allowance is in the JSON report next to the bed so that an authorisation bound to the hash knows what was checked.
- **A test grid made from the library of materials, with the figures burnt next to it:** `phoenix-laser calibrate OUT.nc --material NAME --materials FILE` spreads the powers and the feeds of the grid around what the material says (`--steps` values, 5 by default, from `--spread` percent below to the same above, 40 by default), rounded, held between 1 % and the limit of power and between 10 mm/min and the limit of speed and given once each, so the ladder never asks for more than the limits allow; a material over a limit is refused, never lowered, and `--powers` or `--feeds` still win. `--labels` burns the power of each column below it and the feed of each row on its left with a font of strokes (`--label-mm` is the height of the figures, 3 by default), at the power and the speed of the material, and moves the squares to make room, so a grid that was burnt can be read on the material long afterwards; `--no-labels` takes them off when the file asks for them. The new `[calibrate]` section (`steps`, `spread_percent`, `labels`, `label_mm`) holds the usual values, and the output is never written over the library or the settings.
- **The JSON report of `verify` is a record that can be kept next to an authorisation:** besides the SHA-256 of the program and the verdict it now says the machine profile that was chosen (`machine.profile`), the SHA-256 of the settings file the limits were read from (`machine.config_sha256`) and the names of the checks that were made (`validations`: the moves, the limit of power, the limit of speed, the laser off during rapid moves, a feed on every burning move and, when the size of the bed is known, the bed), so that a change to the program, the profile or the settings afterwards can be seen and the person who authorised knows what was looked at. Both are `null` when no settings file or profile was used.

## [0.0.8] - Machine profiles with limits of power and speed, a trace of a picture, the tone curve, the materials, the focus test, the frame and the preview in the window and a check of a G-code program

- **A check of a program that gives its hash:** `phoenix-laser verify PROGRAM.nc` reads a G-code program (this program's or another's) as text, never runs it, and prints the SHA-256 of the exact file, what it does (moves, burnt and travelled length, time, box, highest power and speed) and a verdict. It passes only under the limit of power and of speed of the machine (from `--config`, `--profile`, `--max-power` and `--max-speed`), inside the bed, with the laser off during every rapid move and a feed on every burning move; the end of the program and the other warnings are notes. `--json` prints the report in a form another program can keep next to an authorisation bound to the hash, and the exit code is 1 when the program fails.
- **The preview in the window:** the G-code that the window works out is counted by the same preview as `phoenix-laser preview` (moves, burnt and travelled length, a time that counts the corners with the acceleration of the box) and its warnings, such as work outside the bed of the settings file or a power above full, are listed in a new group of the side panel. A G-code program of any origin (`.nc`, `.ngc`, `.gcode`, `.gc`, `.tap`) can be opened from a button or dropped on the window to see its path and its warnings; it is read as text, never run, and the window refuses to write it again.
- **The frame in the window, with a question before the laser is lit:** a new mode frames the picture or the drawing that is open (the box of what burns, the same as `frame --gcode`), with the margin, the laps and the speed as boxes that start from `[frame]`. The laser stays off with a pilot power of 0. A pilot power above 0 turns the laser on, so the window asks first and nothing is worked out or written until the person answers yes: the answer is taken back by any change to a box, by a change of mode and by writing the file, so every run asks again. The pilot power is under the cap `max_pilot_percent`, the limit of power and the bed of the settings file, and a pilot power in the settings file is only a value shown in the box.
- **The focus test in the window:** a new mode, with the boxes of the `[focus]` section of the settings file, works the test out with the same function as `phoenix-laser focus` and draws its lines. Its power and speed obey the limits of the window, the step of the height has no default (the test is refused until it is given, because which way is down depends on the machine), a warning that the test moves Z stays in the notes, and the G-code is written with the same header as the command line.
- **A tone curve in the settings file:** the new `[tone]` section (`gamma`, `contrast`, `brightness`, `invert`, `auto_level`) is the starting point of `engrave --config`, under a material and the options `--gamma`, `--contrast`, `--brightness`, `--invert` and `--auto-level`, and the starting values of the boxes of the window.
- **Tone, materials and limits in the window:** the boxes of the tone curve (with switches for invert and auto level) work the picture out with the same function as the command line, so the window and `engrave` write the same G-code. A library of materials is loaded from a file or from `PHOENIX_LASER_MATERIALS`, and a material chosen from the list fills the boxes of the power, speed, dot, dithering and tone, and the table of layers of a drawing. The limits of power and of speed are boxes (they start from `[machine]`) and the window refuses a power, a speed or a grid over them, never lowering it. The words of all of this are in the eight languages.
- **Contours from a picture:** `phoenix-laser trace IMAGE OUT.nc --width-mm W` follows the outline of a logo, a silhouette or a stencil instead of burning it dot by dot. The grey levels are split at `--threshold` (ink under it, over it with `--invert`), the border is found with marching squares that place every crossing by the grey levels on both sides of it, the rings are simplified with the Douglas-Peucker rule until no point is farther than `--simplify` mm from the line, and rings smaller than `--min-area` mm2 are dropped. The result is a layer called `trace`, cut (or filled with lines with `--engrave`) with the settings of the file and the options of `cut`, with the same checks of the G-code. The new `[trace]` section holds the defaults and the limits (`max_pixels` reduces a big picture, `max_contours` and `max_segments` refuse a picture that is too detailed).
- **Machine profiles:** a `[profile NAME]` section of the settings file describes a machine and laser (`travel_x_mm`, `travel_y_mm`, `max_power_percent`, `max_speed_mm_min`, `s_max`, `laser_watts`), so that a person with two machines, or a laser module that is changed for another, keeps one profile for each in the same file. The profile that is chosen with `profile = NAME` in `[machine]` or with `--profile NAME` (on `engrave`, `calibrate`, `cut`, `vector`, `layers`, `focus`, `frame` and `preview`) is the machine: its values win over `[machine]` and the options of the command line win over both. The limits of the profile hold over the layers and the defaults, a profile that is not in the file is an error that lists the ones that are, and `--profile` without `--config` is an error.
- **A limit of speed that refuses instead of lowering:** `max_speed_mm_min` in `[machine]` (30000 by default) and `--max-speed` on the commands that take a limit of power. A layer, a `--feed`, a `--feeds`, the frame or the focus test that asks for more is an error that names it, the way a power over the limit of power already is.
- **The cap of the pilot power of the frame is a setting:** `max_pilot_percent` in `[frame]` (5 by default, from 0 to 100; 0 allows no pilot power at all) replaces the fixed 5 %. The limit of power of the machine (`max_power_percent`) still holds over it, a `pilot_percent` above the cap is an error of the file, and `--confirm-laser-on` is still needed on every run.

## [0.0.7] - A tone curve, ordered dithering, a limit of power, a library of materials, a preview of the program, a frame with the laser off and a focus test

- **Focus test:** `phoenix-laser focus OUT.nc --z-step MM` writes a ladder of short lines side by side, each burnt with the head at another height, so that the sharpest and thinnest line shows where the beam is in focus; it goes back to the first height at the end. The step of the height has no default, because which way is down depends on the machine and a head sent the wrong way can hit the material; the power of the test obeys the limit of power. The usual values (first height, step, number of lines, length, spacing, feed, power) live in the new `[focus]` section of the settings file, and the output is never written over that file.
- **The strings of the tests of the limit of power and the frame are written on one line each,** the way the other tests of the settings file write them.
- **The frame of the work, with the laser off:** `phoenix-laser frame OUT.nc --size W,H` (from the corner `--origin`) or `--gcode PROGRAM.nc` (the box of what burns in a program, so its real place is framed) writes a program that traces the rectangle, `--margin` wider and `--laps` times, to see where the work will land on the material. The laser stays off: no power is set and the spindle is never turned on. A weak pilot power (`--pilot`, at most 5 % and at most the limit of power) needs the words `--confirm-laser-on` on every run, even when the settings file asks for it, and the program turns it off before it ends. A frame outside `--bed` is an error. The usual values live in the new `[frame]` section of the settings file (`feed_mm_min`, `laps`, `margin_mm`, `pilot_percent`).
- **Preview of a G-code program:** `phoenix-laser preview PROGRAM.nc [OUT.svg]` reads a program (this one's or another's; G0, G1, arcs as lines, millimetres or inches, absolute or relative) and prints its moves, the burnt and travelled length, the box of the work, the powers and a time that counts the speed and the braking at every corner (`--accel`, `--rapid`). It also warns of what looks dangerous: the laser on during a rapid move, a burning move with no feed, `S` above `--smax`, work outside `--bed` and a program that does not end. With an output file it draws the path as an SVG, the travel thin and dashed and the burn in a colour that deepens with the power. It only reads text, takes the machine from `--config`, and never writes over its program.
- **A library of materials:** a plain text file with a `[material NAME]` section for each material and way of working (power, speed, passes, focus step, beam width, hatch and, for a picture, dot size, overscan, dithering and tone curve). `--material NAME --materials FILE` (or `PHOENIX_LASER_MATERIALS`) applies one to `engrave`, `cut`, `vector` and `layers` under the options of the command line, `phoenix-laser materials FILE` lists a library, `examples/materials.cfg` shows every key, and the limit of power still holds over a material. A value out of range, an unknown key or a name used twice is an error that names the line, and the output is never written over the library.
- **A limit of power that refuses instead of lowering:** `max_power_percent` in `[machine]` (100 by default) and `--max-power` on `engrave`, `calibrate`, `cut` and `vector`. A program whose power is over the limit is an error that names the option or the layer, so what is written is always what was asked for. `engrave` and `calibrate` take `--config FILE` to read the limit and `s_max` from the `[machine]` section of the same settings file as the other commands, and never write their output over that file.
- **Ordered dithering (Bayer):** `engrave --dither bayer` decides every dot by its own place and grey with an 8 x 8 Bayer matrix, so the pattern is regular and a grey burns the same dots every time; it is also in the list of dithering methods of the window, in the eight languages.
- **Tone curve for a picture:** `engrave` takes `--gamma`, `--contrast`, `--brightness`, `--invert` and `--auto-level`, which change the grey levels with one table of 256 entries before the dots are made (`src/tone.rs`). The default values leave the picture exactly as it is, and a value out of range is an error that names it.
- **The README says the maturity of the manifest:** the badge and the Maturity row of the eight READMEs read functional, as the manifest does, and the check of the status lights now fails when they differ.
- **`engrave` and `calibrate` write their file the way `cut` does:** through a temporary file that replaces the output only when it is complete, so a full disk leaves no half program under the final name; `engrave` refuses an output that is the image it is made from; `--smax` of both takes a whole number only (1000.7 is an error instead of 1000).
- **A name in a comment of the G-code loses the characters GRBL obeys at once:** `!`, `~` and `?` become `_` in the layer names written to comments, as the common header already does.
- **No rapid move of the image or of the test grid travels with a power set:** the image writer and the grid write `S0` before a `G0` when the line before burned and nothing had put the power to zero (an image without overscan, the squares of the grid). Tested by reading the power in force at every rapid move.

## [0.0.6] - Shared tools in step and pins on the newest releases

- **The shared validation tools are updated:** the validator also runs the workflow and lessons checks of the suite with their latest rules, including a check to run before every push.
- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and the check of the CHANGELOG is a job of its own.
- **The shared tools are the ones of the suite:** `ci_validate.py`, `make_structure.py` and `make_architecture.py` are the canonical copies of the documentation hub, and the architecture picture is drawn again with them.
- **The CI is split in two workflows:** the validation of the repository (manifest, documentation, pictures, tools) stays in `ci.yml` and the Rust jobs move to `rust.yml`, which does not run for a change that only touches Markdown files or pictures, so a change of the documentation no longer builds the code on two systems, and they keep a cache of the build. The names of the jobs are the same.

- **The pins follow the new releases:** the CI and the release build take `EH3D-COMMON` at `v0.2.1` and `EH3D-CORE-LIBS` at `v0.0.9`, and the manifest asks for `min_common` 0.2.1.

## [0.0.5] - Energy by layer, picture mode and strict G-code header

- **The Rust toolchain is pinned:** `rust-toolchain.toml` fixes the version of Rust (the same one in every repository of the suite) with `rustfmt` and `clippy`, the workflows install that version and not `stable`, so a new release of Rust cannot turn the CI red by itself.
- **Fuzz tests with a fixed seed:** every cut of the example DXF and SVG drawings, 600 damaged copies of them and bytes that are not a drawing are read without a panic and without a shape that holds a number that is not finite.

- **The G-code of the calibration grid and of an engraving is walked in the strict mode of the debugger:** `tests/generated_gcode.rs` reads it back with the reader of the suite and fails on a warning of the reader, a cut with the laser off, a cutting move with no feed or a program that does not end.

- **The number and the header of the G-code are the ones of the suite:** `gcode_out.rs` re-exports `number`, `sha256_hex` and `header` from `eh3d-parser-gcode` (EH3D-CORE-LIBS) instead of keeping its own copies, which are tested there; the CI checks out that repository at its tag next to this one.

- **The energy of a pass for each layer:** the new key `laser_watts` of `[machine]` (the optical power of the laser at full power, 0 to 1000 W; 0 by default, which means it is not known) lets `phoenix-laser layers` end the line of each layer with the energy one pass puts into the material: the power of the layer over its speed in joules for each millimetre of a cut (10 W at 50 % and 600 mm/min is 0.500 J/mm), and spread over the distance between the lines of a hatch in joules for each square millimetre of an engraving (5.000 J/mm2 with lines 0.1 mm apart). It is plain arithmetic in `energy.rs`, with its tests; it says nothing of how a material answers, and with `laser_watts = 0` the lines are the same as before. The key is documented in `docs/vector-settings.md`.
- **A picture mode for the window:** `--shot FILE.png` (built with `--features gui`) opens the window at the size of `--size WxH` (320 to 8192, 1180x760 by default), with `--theme forge|dark|light`, `--lang CODE` and the file of `--open FILE`, waits `--wait N` frames (0 to 3600, 6 by default), saves what it drew as a PNG file and closes by itself. An existing file is never replaced unless `--replace` is given, the window keeps no settings and reads no settings file in this mode, the exit code is 0 when the file was written, 1 when it was not (also when the picture does not come back within 600 frames) and 2 for wrong arguments, and a build without the window says so. The arguments are read by plain code with its tests.

## [0.0.4] - Vector cutting and engraving from SVG and DXF, the window with a table of layers and the Windows icon

- **Ready-made programs for every system:** the `Release binaries` workflow, started by hand by the owner from main, builds the window version for Windows (64 and 32 bits), Linux and macOS (Apple silicon and Intel), packs each with the licence, the README, the icon and the examples, writes the SHA-256 of every package, `SHA256SUMS` and a build manifest, attests their provenance, checks the result as a stranger would and, only when the dry run is switched off and the owner approves, prepares a draft release; the README has a Downloads section that tells how the signed packages are checked.
- **Vector drawings are read:** `svg` reads a safe subset of SVG (`path` with `M L H V C S Q T A Z` absolute and relative, `rect` with round corners, `circle`, `ellipse`, `line`, `polyline`, `polygon`, `transform`, groups, the layers of Inkscape, stroke and fill colours, the units `mm cm in pt pc px` with a settable `dpi`) and `dxf` reads `LINE`, `LWPOLYLINE` and `POLYLINE` with bulges, `ARC`, `CIRCLE` and `SPLINE` (through its fit points, or from its control points, knots and weights) with the unit of the file. Scripts, images, `use`, text, gradients and styles with selectors are never run or fetched and are skipped with a note; a declared entity is an error. Curves become straight pieces that stay within a settable tolerance of the true curve. The size of the file, the depth, the elements, the shapes, the points and the pieces of a curve are limited by settings.
- **Cutting and engraving by layer:** the shapes are grouped by colour (SVG) or layer (DXF); each group is cut or engraved with its own power, speed and passes. Cutting joins loose lines whose ends meet, cuts the contours that lie inside another one first and keeps the travel with the laser off short (the nearest next contour and then a limited 2-opt improvement that never breaks the inside-first rule), moves a closed contour half the width of the beam to the right side (outside a piece and inside a hole, or always one side) with round corners and a check of every edge of the result, leaves tabs uncut on the outline of a piece, and moves the focus on at each pass. Engraving fills closed shapes with lines at an angle and spacing (the even-odd rule, one way and then the other, with overscan) and follows open ones. A contour that is too small or too narrow for the beam is left out with a note instead of being cut wrong.
- **The settings are in a file:** the limits of the readers, how a file is read, the order of the cuts, the machine (full power, overscan, speed of the travel, origin, focus, bed) and the settings of each layer or colour are keys of a plain text file that is checked line by line (an unknown key or a value out of range is an error that names its line); nothing tuned is in the code. `docs/vector-settings.md` has every key with its default and its range, and `examples/plate.svg`, `examples/plate.dxf` and `examples/plate.cfg` show them at work.
- **A G-code that is checked before it is given:** the program of a drawing keeps the form of the one of a picture (`G21`, `G90`, `M4 S0`, `S0` while it travels, `M5` and `M2` at the end) and every line is checked: only the words the program writes, `S` never above full power, no laser on during a rapid move or a move of the focus, no cut without a speed, no move outside of the bed (when its size is given), and a power that rounds to `S0` is refused. A program that fails is not written. The file is never written over the drawing or the settings it is made from.
- **Commands `cut`, `vector` and `layers`:** `cut DRAWING OUT.nc` follows the contours, `vector DRAWING OUT.nc` fills the closed shapes with lines, and `layers DRAWING` lists the layers with what would be done with each; they take `--config FILE` and the options `--power`, `--speed`, `--passes`, `--focus-step`, `--kerf`, `--kerf-side`, `--tabs`, `--tab-width`, `--angle`, `--spacing`, `--smax`, `--overscan`, `--origin`, `--bed`, `--dpi` and `--tolerance` over the settings of every layer, and `--dry-run` works the job out without writing.
- **The window opens drawings:** an SVG or a DXF is opened from the list of files or dropped on the window and the program switches to cutting; the path of the laser is drawn with the cut in one colour and the travel dim, the table of layers (mode, power, speed, passes, step of the focus, width of the beam and its side, tabs, hatch angle and spacing) is edited in the window, a settings file can be loaded, the notes of the reading and of the plan are listed, the time is estimated and the G-code is exported with the same header as the one of a picture. The words are in the eight languages.
- **A window:** built with `--features gui`, `phoenix-laser` with no arguments (or with one picture, or `gui [IMAGE]`) opens a window in the look of the other programs of the suite (amber on charcoal, the icon of the program). A PNG or PGM picture is opened from the list of files of the window or dropped on it; the passes of the laser are drawn as the head makes them (burning in a colour that follows the power, travel and overscan thin), with zoom (wheel) and pan (drag); the width, the size of a dot, the dithering and its threshold, the feed, the power, the full power value, the overscan (typed or worked out from the acceleration) and the origin can be edited, a calibration grid of power against feed can be made, and the G-code is exported with the same header as the command line. The command line works as before, and a build without the feature is only a command line.
- **The window speaks the eight languages:** English, Spanish, German, French, Italian, Japanese, Chinese and Portuguese of Portugal, chosen from the system and changeable in the window.
- **The logic of the window needs no screen:** `window` (picture, settings, engraving, passes, export, status), `viewport` (zoom and pan), `browse` (the list of files) and `lang` (the words) are plain code with their own tests; `gui` only draws them.
- **The Rust version needed is 1.88,** the one the window needs.

- **Renamed:** The project is now called EH3D-PHOENIX-LASER (it was EH3D-LASER-CAM); it joins the PHOENIX family of programs.

## [0.0.3] - Audit fixes, the new reading limits, tests and the application icon

- **The application icon and the logos of the program:** `images/brand/` holds the icon (SVG, PNG sizes, `.ico` and `.icns`), the horizontal and vertical logos in a light and a dark version and the social preview image.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **Every G-code file opens with a standard header:** comment lines with the generator and its version, the units (mm, G21), the picture it was made from with its SHA-256 and the tools (the laser and its power); the calibration grid says it has no source. The library functions keep returning the program alone, so the header belongs to the files the command line writes.
- **One way to write a number, and no `NaN` or `inf` in a file:** the engraving and the calibration grid write every number with the same function (`gcode_out::number`: three decimals at most, no `-0`), and a value that is not finite is an error. The SHA-256 used by the header is written in the program itself (no new dependency) and checked against the known test vectors.
- **The reader of pictures comes from EH3D-COMMON (`eh3d-image`):** the program no longer keeps its own copy of the PGM and PNG reader; it takes it by path from the sibling repository, which must be cloned beside this one. `eh3d_*::image` keeps working as before. The manifest names EH3D-COMMON in `depends_on` and the CI checks it out.
- **More tests:** the G-code read back into the dots it was made from, the limits of the head and of every value, the calibration grid square by square, and the command line with its errors and file names in any script.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, and the checkouts keep no credentials.
- **More tests of the limits:** every value of the parameters at its edges, what the engraving reports, and the shape of the lines at the ends.

## [0.0.2] - Dry run for engraving

- **Strict command line:** an option that is written wrong (`--powr`) or a word too many is an error that names it; before, it was ignored and the output was made with the default values.
- **A dot size that makes no sense is refused before anything is reserved:** `--dot-mm 0` or a tiny one, or an image that would be larger than the limit, gives an error instead of an allocation failure or an overflow.
- **`engrave --dry-run`:** works the engraving out and counts it (dots, lines, runs, burnt length, time), without writing the output file (which may then be left out).
- **One shared helper for the command-line arguments** (`src/cli_args.rs`: flag, switch, num and a strict finish), the same file in every small utility of the suite; the copies this program had behaved the same, so nothing changes for a person.
- **Tests that run what the README and the scripts promise:** the sample of `run.sh`, `run.bat` and the README is the same command, and it is run on the files of `examples/`.
- **The banner of the README** shows the role and the technologies of this program (it showed the text of the shared library).

## [0.0.1] - An image engraved by a laser: dithering, raster G-code with dynamic power and a calibration grid

- **The image:** PNG (grey, colour, transparent, 8 or 16 bits) and PGM, with the size limited; `resize` averages the pixels.
- **The dots:** threshold, Floyd-Steinberg and Atkinson, checked to keep the darkness of a grey.
- **The laser:** `M4` with `S0` while it travels, alternating directions, an overscan fixed or worked out from the acceleration, and the top of the image as the highest Y.
- **The calibration grid:** a square for every pair of a power and a feed.
- **The command line** `eh3d-lasercam` with `engrave`, `calibrate` and `info`, and a sample gradient.
- **18 tests** run on a computer, with damaged input.

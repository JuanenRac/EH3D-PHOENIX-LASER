# Changelog

All notable changes to this project are documented here.

## [Unreleased]

## [0.1.5] - Forbidden zones and simulated interlocks, a 40 percent power ceiling for the server, arcs in G-code, DXF blocks, drawing conversion and a report before a job

- **The settings of the program as a contract:** `phoenix-laser settings [--json]` lists every setting of the program (the keys of the settings file and of a library of materials: section, key, the kind of value, the default and whether it is a safety setting such as a limit, a zone, an interlock or the token of the server), as lines of text or as JSON for a server, a studio or a test to read, so that every switch and number of the program has an entry that can be shown or checked without reading its code. Tests keep the list equal to the keys the reader takes (a key added to one and not to the other fails), every default that is a value is accepted by the reader and equal to the documentation, and the JSON reads back.

- **A report to read before a job, in eight languages:** `phoenix-laser report PROGRAM.nc [--lang en|es|de|fr|it|ja|zh|pt]` writes the check of `verify` as something to read before the program is started: the SHA-256 of the file, the moves, the length burnt and the time, the box of the work, the highest power and speed against the limits, the energy when the power of the laser is set, whether the material of `--material` was verified (or never said), how many forbidden zones were checked, what the interlocks of the settings say, the reasons of a failure and a verdict that says plainly not to run a program that fails. The words are in the language asked for (the one of the system by default; Portuguese of Portugal for `pt`); the reasons that the check gives stay in English, as it writes them, and say so. It reads the file as text, runs nothing, and ends with code 1 when the program fails. A test checks that every text exists in the eight languages with the same places for its values.

- **Drawings written as SVG or DXF:** `phoenix-laser convert DRAWING OUT.svg|dxf` reads a drawing (an SVG or a DXF, with its curves cut into straight pieces within `--tolerance`) and writes it again as a plain SVG (one group for each layer named as Inkscape names its layers, a `polygon` for a closed shape and a `polyline` for an open one, in millimetres with the y axis down) or as the old ASCII DXF of release 12 (`POLYLINE`, `VERTEX` and `SEQEND`, a table of layers, in millimetres, with the colour as the AutoCAD index when it is one of the nine basic ones and always as a true colour), so another program can open what this one understood. The extension of the output chooses the format, a drawing is never written over itself, a drawing with no shape is an error, and the layer names the old form does not allow are written with `_`. The tests read every file back with the program's own readers.

- **DXF drawings with blocks and ellipses:** the DXF reader now draws `INSERT` (a block of the `BLOCKS` section at its insertion point, scale and rotation, with its base point, as an array of columns and rows too, a block inside a block, and an extrusion pointing down), and `ELLIPSE` (a whole one or an arc of it, cut into pieces within the tolerance of the reader). The entities of a block that are on layer 0, or have no colour, take the layer and the colour of the `INSERT`, the insertion point is in the unit of the file, and what a block adds counts against the limit of entities, how deep blocks nest is limited by `max_depth` (a block that draws itself is an error, not a loop) and an `INSERT` of a block the file does not define, or with a scale of 0, is skipped with a note. Before, both were skipped.

- **What is sent to the server is held to 40 % of the power by default:** the laser plugin of the server is a simulator that refuses more than 40 % of full power until its own limit is changed, so the program now holds a program, a vector job and a test fire to the lower of the limit of the machine and the new `max_power_percent` of a `[send]` section (40 unless the file says another, from 0.1 to 100) before anything leaves, and says which of the two limits it was; a drawing that asks for more says so by layer. Nothing local changes: the engraving, the cutting and the other commands keep the limit of the machine alone.

- **The ceiling of a material holds over the command line:** `engrave` and `cut` refuse a power or a speed (from the library, from `--config` or from `--power` and `--speed`) that is over the `max_power` or `max_speed` of the material in use and say which layer asked for it, and the ladder of `calibrate --material` is held below that ceiling as well as below the limits of the machine; nothing is lowered quietly.

- **Materials say whether they were verified and how far they may be pushed:** a material of a library can carry `verified` (`off` says its values are only a place to start from), `max_power` and `max_speed`, its own ceiling. A library whose `power` or `speed` is over the ceiling of its own material is refused when it is read, the list of `phoenix-laser materials` marks each entry `[verified]` or `[not verified]` (an entry that says nothing is left unmarked, as before), using a material that is `verified = off` prints a note on the error output to try it on a scrap first, the marks are written back and kept when a material is edited in the window, and the file keeps what it says when it is rewritten.

- **A starter library of materials:** `examples/materials-starter.cfg` holds seven places to start from for a weak diode laser (plywood cut, engraved and as a picture, cardboard, paper, leather and black acrylic), every one marked `verified = off` with a ceiling of its own and a note on what to watch; the values are round numbers from general experience, not copied from any table, and nobody has tried them on a real machine.

- **Forbidden zones of the bed:** a `[zone NAME]` section of the settings file (`x_mm`, `y_mm`, `width_mm`, `height_mm` and `kind`) names a rectangle, in millimetres of the machine, where the beam must not burn (`no_burn`: the head may cross it with the laser off) or where the head must not go at all (`no_go`, which a zone has when its kind is not said). A program that reaches a zone fails `phoenix-laser verify` (with the zone, how many moves reach it and the line of the first), the check of the window and the check before a program is sent to the server, and a drawing sent as a vector job is refused when one of its paths reaches a zone of either kind; the edges of a zone count as inside, the arcs of a program are checked along the curve, and a zone with no size, a name that is empty, a number that is not one or more than 64 zones are refused when the file is read. The report of `verify --json` lists `forbidden_zones` among its checks when there are zones.

- **Interlocks held in the settings file:** an `[interlocks]` section (`estop` as `released` or `pressed`, `enclosure` as `closed`, `open` or `unknown`, `air_assist` as `on`, `off` or `unknown`, and `require_enclosure` and `require_air_assist`) says what the machine is doing, because this program reads no sensor: a simulator, a gateway or the person writes it. A pressed emergency stop, and a required interlock that is not in its safe state (a state that is not known counts as unsafe), fail `verify`, stop the program, the vector job and the test fire from being sent, and say why; with the defaults (nothing required, the stop released) nothing changes, and the report lists `interlocks` among its checks only when they are active. Nothing here has been tried against a real sensor or a real emergency stop.

- **`G92` moves the origin in the reading of a program:** a program that says `G92 X0 Y0` (the head stays where it is and the program calls that place 0, 0) is read in the places where the head really goes, so the box, the burnt length and the check against the bed (`preview`, `verify`, the check before a program is sent) are no longer worked out from the numbers of the program alone; `G92.1` and `G92.2` take the name back, and a line with `G92` is not counted as a move. The words that choose other coordinates in the controller (`G10`, `G28`, `G30`, `G53`, `G54` to `G59.3`) are told in the notes, because there the places of the report are the ones the program writes.

- **The arcs of a program are drawn as arcs:** a program with `G2` and `G3` (in the form with the centre `I`, `J`, in the form with the radius `R`, and as a full circle when the end is left out) is cut into straight pieces no farther than `arc_tolerance_mm` of `[verify]` (0.01 mm unless the file says another, from 0.0005 to 1) from the true arc, so that the length, the time, the energy, the box and the check against the bed of `preview`, `verify`, `frame --gcode` and the check before a program is sent follow the real curve, which can reach past the bed where its two ends do not (before, an arc was counted as a straight line to its end). The centre as a point (`G90.1`) and the plane of the arcs (`G17`, an arc in `G18` or `G19` is told and drawn straight) are read, an arc whose two ends are not at the same distance from its centre is told like GRBL refuses it, a radius too short for its ends is told, and `G90.1` and `G91.1` no longer count as `G90` and `G91` (the way the moves are positioned).

- **A picture of any window of the program:** `--window NAME` with `--shot` shows one window of the program in the picture: one of its modes (`engrave`, `calibrate`, `cut`, `focus`, `frame`, `preview`, `trace`, `text`, `qr`, `marks`, `barcode`) is chosen, or `server` holds the section for the server open, which is how the panel of the server of the window is photographed for the README. The name is read in any case, a name the window does not have is refused with the list of names, and `--window` without `--shot` is refused like the other options of the picture; the picture still keeps no settings. The reading of the name is tested without a screen.

- **The pictures of the window are taken again with the newest build:** the two pictures of `images/screens/` come from the Windows 64 bits program of the latest release.

## [0.1.4] - Server panel in the window, test fire and vector jobs, alignment from a camera picture, labels of the material editor and layer times with acceleration

- **The time of each layer, with the head braking at the corners:** `phoenix-laser layers DRAWING --accel A` (1 to 100000 mm/s2) also prints, under each layer that is burnt, how long it takes with the head braking and speeding up at every corner at that acceleration and how much of that time the laser burns, and the total of all the layers. The whole drawing is planned once, as it would be written, the program is cut at the comment that opens each layer, and each piece is read by the preview of the program, so the burning times add up to the one of the whole program; each piece starts with the head at the origin, so the rapid move to its first contour is counted from there. Without `--accel` the output is the same as before.

- **Where the material lies, from a picture of the bed:** `phoenix-laser align PICTURE.pgm|png --size W,H --px-per-mm S` finds the positioning marks (the ones `marks` burns, with the same size, origin, arm, margin and centre cross, or the `[marks]` of `--config`) in a picture of the bed taken from straight above, with the machine axes along the rows and the columns and the origin of the machine at the lower left corner, and says how far they lie from where they should be: the shift to add to the origin of the work (`--origin` of the next command is printed), the turn in degrees and how far the marks are from lying as one piece. It refuses a picture in which a mark is missing or further than `--max-shift-mm` (20 by default) from its place, a turn over `--max-angle-deg` (5 by default) and marks that do not move together, and the dust and the smudges of a picture are left out. `align --simulate OUT.pgm --shift DX,DY --turn DEG` draws the picture a simulated camera would take of the marks moved and turned by a known amount, which is what the tests read back to a fraction of a millimetre and of a degree; nothing has been tried on a picture of a real camera, a real lens or a real bed.

- **Tests with a fixed seed for the way to the server:** random layer names (quotes, backslashes, controls, accents and characters of several bytes), random paths and random operations go through the request of a vector job and come back from the JSON reader as they went; a vector job with random points and powers is refused or passes the check against the limits of the machine without a panic; random powers and times of a test fire are refused or sent as numbers that read back; and a damaged answer of the server (cut, with bytes changed, or not JSON) is read as a job, a machine or a test fire without a panic.

- **The panel of the server of the suite in the window:** the section for the server of the window now shows the panel every program of the suite shows (`eh3d-view` of EH3D-COMMON) instead of leaving the address, the token and the machine to the settings file: the boxes for the address, the token of the program, the id of the machine and the limits of the link, a button that tests the connection, the state of the link with its badge, and a login with a name and a password for the application `laser`, which keeps the token in memory only and uses it for the job that is sent when the settings give none. What is applied in the panel is used from then on; the settings file is not rewritten. The section is always there (closed while no server is set), and the words of the panel come in the language of the window.

- **A program that was opened can be sent after the check:** a G-code program opened to be seen, which was never sent before, goes to the server as it is (nothing is added to it and it is never written) when the check of the window passes for exactly the bytes that are open (the same SHA-256), the check against the limits of the machine passes too, and the person ticked the box that says the program is sent as it is; the box is asked again for every program that is opened, and a program that fails the check, or whose text changed after it, is refused with the reason.

- **Marks sized from the work:** the marks mode has a button, `Size from the work`, that puts the width and the height of what the open picture, drawing or outline burns (the box the frame takes, rounded up to a hundredth of a millimetre and at least 1 mm) in the boxes of the marks, so that they go round exactly the work.

- **Labels of the values of a material in eight languages:** the editor of materials names each of the seventeen boxes (power, speed, passes, focus step, kerf, hatch spacing and angle, cross hatch, dot size, overscan, dithering, threshold, gamma, contrast, brightness, invert and auto level) with a word in the language of the window and keeps the key of the file beside it.

- **A test fire and a drawing sent to the server:** `phoenix-laser server test-fire --power-percent P [--seconds S] --confirm-fire` fires the laser for a moment with no job, to find the focus, through the `laser/test-fire` route of the `laser` plugin; the power is above 0 and up to the limit of power of the machine of the settings, the time is from 0.01 to 10 seconds, and because it lights the laser it is not sent without `--confirm-fire`; the server refuses it while a job runs, while an emergency stop holds the machine, with the enclosure open or the air assist off and above its own limit of a test fire, each refusal told by its code in the language of the system, and a test fire is never sent twice. `phoenix-laser server vector DRAWING.svg|dxf [--follow]` sends a drawing as a `vector` job: the paths of the layers that are not skipped in the millimetres of the machine and one operation for each layer from the settings (`cut` or `engrave`, power, speed and passes, with the options of the drawing commands over them), after the limit of power and of speed and the bed of the settings have been checked; the plugin of the server makes its own program from the shapes, so a note says which layers asked for a kerf, tabs or a hatch that it does not apply. Tested against the stand-in of the plugin, in memory and on a socket of this computer.

- **The refusals of the laser plugin come from the shared catalog:** the six codes of the `laser` plugin of the server (`laser_estop_latched`, `laser_power_limit`, `laser_feed_limit`, `enclosure_open`, `air_assist_off` and `test_fire_refused`) are now told with the text of the catalog of the suite (`eh3d-serverclient` of EH3D-COMMON, in the eight languages) and the table this program kept for them is gone; the builds of the CI and of the binaries check out EH3D-COMMON at v0.2.6, which brings those codes, the panel of the settings of the server of the window and the headers of the client.

## [0.1.3] - Window modes for marks, barcodes and focus by power, editable materials and the server mode with emergency stop

- **Send to the server from the window:** when the settings file gives a server (`[server]`), the window has a section with a button that sends the program it has worked out as a job of the laser machine of the server, shows how far the job is, and holds it, lets it go on or stops it with an EMERGENCY STOP button that ends it at once and latches the machine; the program goes after the same guards as the export (a program that was opened to be seen, or a frame that lights the laser and was not confirmed, is not sent) and the check against the limits of the window and the machine of the settings, and a machine that an emergency stop holds says so instead of taking a program. Closing the window leaves the job where it is on the server.

- **Sending to the EH3D server:** a new `[server]` section (`server_address`, `server_token`, `server_machine`, `server_timeout_s`, `server_retries` and `server_mdns`, the keys every program of the suite reads, with the token never printed) and the command `phoenix-laser server status|send|job|pause|resume|stop|release` work with the `laser` plugin of EH3D-SERVER through the shared client of the suite (`eh3d-serverclient` of EH3D-COMMON, which is now a dependency by path): `send` checks the program against the limits of the machine of the settings (the limit of power and of speed, the bed) and does not send one that fails, makes it a G-code job of the laser machine and, with `--follow`, stays until it ends; `pause` and `resume` hold it and let it go on; `stop` is the emergency stop, which ends the job at once and latches the machine so that no program is taken, or sent, until an administrator runs `release`; the refusals of the server, those of the laser plugin included, are told by their code in the language of the system. The local modes are not touched. Tested against a stand-in of the plugin, in memory and on a socket of this computer; the plugin of the server is a simulator, and nothing has run against a real laser.

- **Materials edited from the window:** a material of the library can be edited, copied, made from the boxes of the window (the power, the speed, the dot, the overscan, the dithering and the tone curve) and deleted, and a new library can be created, from the material section; a value is typed in a box for each key of the file and is saved in the file of the library by rewriting the section of that material in its place (or adding it at the end), so the comments, the blank lines, the order, the line ends and every other material stay as they were. A value out of its range, a name that is empty, too long or already used, a note that is too long, a file that is not UTF-8 text or that is not a valid library, or a library that would pass the limits of size is refused with the key named and the file untouched, never cut down; deleting asks to press the button a second time, and a new library is never written over a file that is there.

- **Code 128 barcode in the window:** a new mode has a box for the data, a switch for the mirror image and one box for each key of `[barcode]` (the width of the narrowest bar, the height, the distance between the lines, the power, the speed, the passes, the most characters, the widest barcode, the most burning moves and the longest burning), a settings file fills them, and the barcode is worked out with the same function as `phoenix-laser barcode` from the origin of the machine, so data that is not printable text or is too long, a barcode over a limit, a power or a speed over the limit of the machine or work outside of the bed is refused with the box or the reason named in the status line; it is written as `barcode.nc` with the usual header.

- **Positioning marks in the window:** a new mode has boxes for the size of the rectangle, the arm of each L, the margin, the power, the speed and the passes, and a switch for the cross in the middle, a settings file fills the boxes of `[marks]`, and the marks are worked out with the same function as `phoenix-laser marks` from the origin of the machine, so an arm longer than half a side, a power or a speed over the limit or marks outside of the bed are refused with the box or the reason named in the status line; the program is written as `marks.nc` with the usual header.

- **Focus grid of powers in the window:** the focus mode has a box for the powers of the grid (up to 10 percentages, separated by commas): with powers in it the window burns the lines of the focus test once for each power, a column for each, with the same function as `phoenix-laser focus --powers`, the box of the single power is left out while it is used, and a power that is not more than 0 up to 100, one over the limit of power, too many powers or a missing step of the height is refused with the box named.

- **The power of the laser in the window:** a box for the optical power of the laser (0 means it is not known; the settings file and a machine profile fill it from `laser_watts`) makes the preview of what the window works out or opens tell the energy that the program burns and its mean power, with the same arithmetic as `phoenix-laser preview --laser-watts`, and a value that is not a number from 0 to 1000 is refused with the box named.

## [0.1.2] - Code 128 barcodes, positioning marks, energy in the preview and focus grids by power

- **Tests with a fixed seed for what the program writes and reads:** random data (figures, printable characters, controls, accents and characters of several bytes) goes through the text, the QR code and the barcode and is refused or burnt, and what is burnt passes the check, stays inside the bed, never holds the data and, for the barcode, reads back into the data; random numbers in the settings of the barcode and of the marks, in the powers and the steps of the focus grid and in the machine are refused or burn inside the limits of the machine; G-code and a settings file with bytes changed, cut or inserted are read by the preview, the check and the settings reader without a panic and with finite numbers; the same work is written byte for byte every time; and every command of the help has its line in the eight READMEs. A barcode whose origin is not a number from -100000 to 100000 is now refused, as the marks already did.

- **A focus grid of powers:** `phoenix-laser focus OUT.nc --z-step MM --powers 10,20,30` burns the lines of the focus test once for each power (up to 10, a column for each, side by side and in the order given), one row for each height, so the power that burns the thinnest line at the height of the focus can be read off. The head goes to each height once and burns every column of that row, and goes back to the first height at the end. Every power obeys the limit of power of the machine and must be more than 0 up to 100 and at least one step of `S`; no powers, more than 10, `--power` together with `--powers` and a missing step of the height are refused and nothing is written. Without `--powers` the test is the same as before.

- **The energy of a program in the preview:** `phoenix-laser preview PROGRAM.nc --laser-watts W` also says the energy that the program burns, worked out from the power of every burning move as a part of the full power of the controller (`--smax`, or the machine of `--config`, and 1000 when neither says it) over the time it burns at its feed, and the mean power over the time of the burning. The report keeps the time of the burning apart from the time of all the moves (`burn_seconds`), the corners cost time but no energy, a program that burns nothing says so, and a power of the laser outside of 0.01 to 10000 W, or one that has no full power of the controller to go with it, is refused.

- **Positioning marks:** `phoenix-laser marks OUT.nc --size W,H` burns an L at each corner of the rectangle of the work (on its edges, or `--margin-mm` outside of them) at a low power, and with `--centre-cross` a cross in the middle, so that the material can be put back in the same place and a second job lined up with the first. The new `[marks]` section holds the usual values (`arm_mm`, `margin_mm`, `power_percent`, `speed_mm_min`, `passes` and `centre_cross`). Unlike the frame, which is traced with the laser off, the marks are burnt: the power and the speed obey the limits of the machine, and an arm longer than half a side of the rectangle that the marks go round or marks that would go outside of the bed (the margin counts) are refused and nothing is written, never cut down.

- **A Code 128 barcode:** `phoenix-laser barcode OUT.nc --text DATA` burns some data as a Code 128 barcode of the program's own: the characters from space to `~` in set B, and a text made only of an even number of figures in set C (two figures to a symbol, half as wide), each with its check symbol and its stop symbol, filling every bar with lines along its height (`--module-mm` is the width of the narrowest bar, `--height-mm` the height of the bars and `--line-mm` the distance between the lines). The new `[barcode]` section holds the usual values (`module_mm`, `height_mm`, `line_mm`, `power_percent`, `speed_mm_min`, `passes`, `max_chars`, `max_width_mm`, `max_lines`, `max_minutes` and `mirror`). A byte that is not a printable character, more than `max_chars` characters, a barcode wider than `max_width_mm`, a fill of more than `max_lines` moves, a burning that would take more than `max_minutes`, a power or a speed over the limit or work outside of the bed is refused and nothing is written, never cut down, and the data is never written into a comment of the program. `--mirror` burns the mirror image for the back of glass or acrylic. The tests read the program back into the data with their own reader; no scanner has read a burnt barcode yet.

## [0.1.1] - Inverted and mirrored QR codes, text alignment, time limit and pictures of the window

- **A burnt border around an inverted QR code:** `phoenix-laser qr --invert --border-modules N` (or `border_modules` in `[qr]`, from 0 to 8 and 0 by default) also burns a border N modules wide around the inverted symbol, so the symbol is left bare in a burnt plate with no margin of its own. The square with its border counts as the symbol for `--origin`, the bed, `max_size_mm`, the most burning moves and the time of the burning, a border without `invert` is refused instead of being ignored, and the comment of the program and the size that the command and the window report include it. The window has a box for it that a settings file fills.

- **A limit on how long a text or a QR code may burn:** the new `max_minutes` key of `[text]` and `[qr]` (and `--max-minutes` on `text` and `qr`; 240 by default, from 1 to 1440) holds the time of the burning itself, worked out as the length of every burnt line over the speed with all the passes together. A text or a symbol that would take longer (a very low speed, many passes or a very dense fill) is refused with the time it would take and the limit, and nothing is written; it is never shortened. The window has a box for it in each mode, in the eight languages, that a settings file fills.

- **Rows of a text aligned:** `phoenix-laser text --align left|center|right` (or `align` in `[text]`) sets where the rows of a text of several lines start: at the left edge of the text (the default, as before), centred on it or ending at its right edge. The box of the text, the strokes that are burnt and the limits are the same, a text of one row is the same whatever the alignment, a word that is not an alignment is refused with the three that are, and it works with the mirror image. The window has a choice for it, in the eight languages, that a settings file fills.

- **Mirror image of a text and of a QR code:** `phoenix-laser text --mirror` and `phoenix-laser qr --mirror` (or `mirror = on` in `[text]` and `[qr]`, and `--no-mirror` to undo it) burn the work as its mirror image, so that it can be burnt on the back of glass or acrylic and read from the front. The box of the work, the length burnt and the limits are the same as without it, an inverted QR code can be mirrored too, and the comment of the QR program says it. Both are off by default, and the window has a switch in each of the two modes that a settings file fills.

- **A run-up for the fill of a QR code:** `phoenix-laser qr --overscan-mm MM` (or `overscan_mm` in `[qr]`, from 0 to 20 mm and 0 by default) runs the head up to each burnt line from MM before its start and out MM past its end with the laser off, so the head is at speed all along the burnt part. The same lines are burnt at the same power; only the moves with the power at zero are added, and no rapid move comes with the power set. A run-up that would leave the bed (the first and the last modules of the symbol plus the run-up on each side) or a value out of range is refused and nothing is written, never trimmed. The window has a box for it, filled by a settings file.

- **An inverted QR code:** `phoenix-laser qr --invert` (or `invert = on` in `[qr]`, and `--no-invert` to undo it) burns the light modules of the symbol instead of the dark ones, so the symbol is left bare in a burnt plate. It is off by default. The same limits hold over the light modules (the most burning moves, the power, the speed and the bed), the comment of the program says it is inverted, and the window has a switch for it that a settings file fills.

- **Screenshots in the README:** a Screenshots section in the eight languages shows two pictures of the window taken by the program itself with `--shot` (a drawing being cut, with its table of layers, and a picture being engraved, coloured by power), kept in `images/screens/` under 400 KiB each, and the tree of files and the Repository Structure picture list the folder.

## [0.1.0] - Text and QR codes, material grids in the window, cross hatch and a verify that checks the program hash

- **QR code in the window:** a new mode has a box for the data, a choice of the level of error correction and one box for each key of `[qr]` (the side of a module, the distance between the lines, the power, the speed, the passes, the most bytes, the largest version and side, and the most burning moves), a file of settings fills them, and the symbol is worked out with the same function as `phoenix-laser qr` from the origin of the machine, so data that does not fit, a symbol over a limit, a power or a speed over the limit of the machine or work outside of the bed is refused with the box or the reason named in the status line; it is written as `qr.nc` with the usual header.
- **QR code:** `phoenix-laser qr OUT.nc --text DATA` burns data as a QR code of the program's own: versions 1 to 4 (21 to 33 modules a side) in byte mode, the four levels of error correction (`--ecc L|M|Q|H`, Reed-Solomon) and the mask with the lowest penalty, filling each dark module with lines (`--module-mm`, `--line-mm`); `--print` shows the symbol as text. The new `[qr]` section holds the usual values (`module_mm`, `line_mm`, `power_percent`, `speed_mm_min`, `passes`, `max_bytes`, `max_version`, `ecc`, `max_size_mm`, `max_lines`). Data over `max_bytes`, a version over `max_version`, a symbol larger than `max_size_mm`, a fill of more than `max_lines` moves, a power or a speed over the limit or work outside of the bed is refused, never cut down or shrunk, and the data is never written into a comment of the program.
- **Text in the window:** a new mode has a box for the words and one box for each key of `[text]` (the height of a capital, the tallest letter, the gaps between letters and rows, the power, the speed, the passes and the most characters), a file of settings fills them, and the text is worked out with the same function as `phoenix-laser text` from the origin of the machine, so a letter that the font has not, a text over a limit, a power or a speed over the limit of the machine or work outside of the bed is refused with the box or the reason named in the status line; it is written as `text.nc` with the usual header.
- **Text in the security notes and in the architecture picture:** `SECURITY.md` now says what each command writes (and that it is never written over a file it is made from), the security table of the README in the eight languages has a row for the limits of the text, and the architecture picture and its description show the text command and the engraving of a picture as one box, with no stale test count.
- **Cross hatch in the window and in the library of materials:** the table of layers of the window has a box for the cross hatch of each layer, a file of settings fills it from `hatch_cross`, and a material of the library can ask for it with `hatch_cross = on` (or turn it off with `off`; a material that says nothing leaves it as it is) like it does for the angle and the spacing of the hatch. The example library asks for it on the engraving of birch.
- **The check can be tied to the program that was authorised:** `phoenix-laser verify PROGRAM.nc --expect-sha256 HASH` fails the program (exit code 1, a problem in the text and in the JSON report) when the SHA-256 of the file is not the 64 hex digits that were given, in any case, and says the one it has, so a program that was changed after it was looked at is not run by mistake. A value that is not 64 hex digits is refused before the program is read.
- **Cross hatch:** a layer that is engraved can be filled twice, with `hatch_cross = on` in its settings or `--cross` (and `--no-cross`) in `vector` and `trace`: after the lines at `hatch_angle` the shapes get a second set at right angles to them, with the same spacing, in every pass. The limit of lines (`max_lines` of `[hatch]`) holds over each set, the energy of a square millimetre that the list of layers gives is doubled, and the burnt length, the preview and the check of the program count both sets. Off by default, so no program changes unless it is asked for.
- **Text with a font of strokes:** `phoenix-laser text OUT.nc --text TEXT` burns a name, a serial number or a mark with a font of the program's own (capitals, figures, space and `. , - + / : ! ? ( ) = _ '`, each a few strokes on a lattice 4 wide and 6 high; lower case is burnt as capitals and a new line starts a row), so no picture and no font file are needed. The height of a capital, the gaps between letters and rows, the power, the speed and the passes are the keys of the new `[text]` section of the settings file (and the options `--height-mm`, `--spacing`, `--line-spacing`, `--power`, `--feed` and `--passes`), at `--origin X,Y`. A character the font has not, a text of more than `max_chars` characters (200 by default), a height over `max_height_mm` (100 mm), a power or a speed over the limit of the machine, or a text that would go outside of the bed is refused and nothing is written; the text is never written into a comment of the program, so a parenthesis in it cannot let the rest of the line through.
- **The check of a program in the window:** a G-code program that is opened to be seen is now also checked by `phoenix-laser verify`, with the limits of the window and the bed of the settings file: the side panel says whether it passes (with the start of its SHA-256, in green) or what is wrong (in red). A new box holds the overscan that is allowed past the bed with the laser off, the same as `overscan_mm` of `[verify]` and `--overscan-mm` (0 by default, from 0 to 100; a value outside of that is refused and the box is named), and a settings file fills it. A program that burns outside of the bed fails whatever the box says. The words are in the eight languages.
- **The grid from a material in the window:** the calibration mode lists the materials of the library and, with one picked, makes the grid with the same ladder as `phoenix-laser calibrate --material` (the power and the speed of the material in the middle, held between the lowest values and the limits, a material over a limit refused). The boxes are the steps, the spread, the lowest power and the lowest feed, and a switch burns the figures next to the squares with the height of its box; a settings file fills all of them from `[calibrate]`. With no material picked it is the grid of the two lists, as before. The words are in the eight languages.
- **The figures come by default with a material, and the lowest power and feed of the ladder are settings:** `phoenix-laser calibrate --material` now burns the power of each column and the feed of each row next to the squares without being asked (`--no-labels` takes them away; a grid made from `--powers` and `--feeds` is the same as ever and has figures only with `--labels`). The two lowest values that the ladder is held at, 1 % of power and 10 mm/min, are now the keys `min_power_percent` and `min_feed_mm_min` of `[calibrate]` with those values by default (more than 0 up to 100, and more than 0 up to 30000), and the example file, the help and the docs say the same.

## [0.0.9] - Trace and machine profiles in the window, uses in SVG, an overscan limit in verify, a test grid from the materials and a fuller verify report

The boxes are the threshold, the simplification and the smallest piece (they start from `[trace]`), with a switch for a picture whose light part is the ink and another to fill instead of cut; the power and the speed are the ones of the laser boxes and obey the limits of power and of speed, and the limits of the picture (`max_pixels`, `max_contours`, `max_segments`) are the ones of the settings file, so a picture that is too detailed is an error and not a slow program. The frame of the window works from the outline too, and the words are in the eight languages.
- **A machine profile can be chosen in the window:** when the settings file describes machines with `[profile NAME]` sections, a new group of the side panel lists them and the one that is picked becomes the machine, like `--profile NAME` does: the boxes of the full-power value and of the limits of power and of speed take its values, the bed of the profile is the one the frame and the preview check, and what a profile leaves out comes from `[machine]` and never from the profile that was picked before. The limits still refuse a power or a speed over them, a profile that the file does not have changes nothing and the error lists the ones it has, and choosing a profile makes the work stale and takes back the answer to the question of the frame. The words are in the eight languages.
- **A `use` in an SVG brings in the element it refers to:** `<use href="#id">` (or `xlink:href`) of a shape, a group or a `symbol` of the same file is read again where the `use` is, moved by its `x` and `y`, under its `transform` and giving it its paint and layer; the element can be in the `defs` or come after the `use`, a `use` can bring in a group that has other `use`, and a `symbol` with a `viewBox` is fitted to the `width` and `height` of the `use`. What a `use` brings in counts against `max_nodes`, `max_depth`, `max_shapes` and `max_points` like any other element, so a file that multiplies itself is an error and not a slow program, and a `use` that leads back to an element that is being expanded is an error that says it is a circular reference. A `use` of another file or an address, with no `href` or of an id the file does not have is still skipped with a note, and nothing is fetched.
- **The overscan of another program can be allowed in `verify`, as far as the person says:** work outside the bed is a failure, and `--overscan-mm MM` (or `overscan_mm` in the new `[verify]` section of the settings file, 0 by default, from 0 to 100; the option wins) lets the head go that far past the bed with the laser off, as the overscan of the hatch lines of another program does. The program then passes with a note that says how far the head goes. A move that burns outside the bed fails whatever the allowance is, a program that goes past the bed by more than the allowance fails with a problem that says both numbers, and the allowance is in the JSON report next to the bed so that an authorisation bound to the hash knows what was checked.
- **A test grid made from the library of materials, with the figures burnt next to it:** `phoenix-laser calibrate OUT.nc --material NAME --materials FILE` spreads the powers and the feeds of the grid around what the material says (`--steps` values, 5 by default, from `--spread` percent below to the same above, 40 by default), rounded, held between 1 % and the limit of power and between 10 mm/min and the limit of speed and given once each, so the ladder never asks for more than the limits allow; a material over a limit is refused, never lowered, and `--powers` or `--feeds` still win. `--labels` burns the power of each column below it and the feed of each row on its left with a font of strokes (`--label-mm` is the height of the figures, 3 by default), at the power and the speed of the material, and moves the squares to make room, so a grid that was burnt can be read on the material long afterwards; `--no-labels` takes them off when the file asks for them. The new `[calibrate]` section (`steps`, `spread_percent`, `labels`, `label_mm`) holds the usual values, and the output is never written over the library or the settings.
- **The JSON report of `verify` is a record that can be kept next to an authorisation:** besides the SHA-256 of the program and the verdict it now says the machine profile that was chosen (`machine.profile`), the SHA-256 of the settings file the limits were read from (`machine.config_sha256`) and the names of the checks that were made (`validations`: the moves, the limit of power, the limit of speed, the laser off during rapid moves, a feed on every burning move and, when the size of the bed is known, the bed), so that a change to the program, the profile or the settings afterwards can be seen and the person who authorised knows what was looked at. Both are `null` when no settings file or profile was used.

## [0.0.8] - Machine profiles with limits of power and speed, a trace of a picture, the tone curve, the materials, the focus test, the frame and the preview in the window and a check of a G-code program

- **A check of a program that gives its hash:** `phoenix-laser verify PROGRAM.nc` reads a G-code program (this program's or another's) as text, never runs it, and prints the SHA-256 of the exact file, what it does (moves, burnt and travelled length, time, box, highest power and speed) and a verdict. It passes only under the limit of power and of speed of the machine (from `--config`, `--profile`, `--max-power` and `--max-speed`), inside the bed, with the laser off during every rapid move and a feed on every burning move; the end of the program and the other warnings are notes. `--json` prints the report in a form another program can keep next to an authorisation bound to the hash, and the exit code is 1 when the program fails.
- **The preview in the window:** the G-code that the window works out is counted by the same preview as `phoenix-laser preview` (moves, burnt and travelled length, a time that counts the corners with the acceleration of the box) and its warnings, such as work outside the bed of the settings file or a power above full, are listed in a new group of the side panel. A G-code program of any origin (`.nc`, `.ngc`, `.gcode`, `.gc`, `.tap`) can be opened from a button or dropped on the window to see its path and its warnings; it is read as text, never run, and the window refuses to write it again.
- **The frame in the window, with a question before the laser is lit:** a new mode frames the picture or the drawing that is open (the box of what burns, the same as `frame --gcode`), with the margin, the laps and the speed as boxes that start from `[frame]`. The laser stays off with a pilot power of 0. A pilot power above 0 turns the laser on, so the window asks first and nothing is worked out or written until the person answers yes: the answer is taken back by any change to a box, by a change of mode and by writing the file, so every run asks again. The pilot power is under the cap `max_pilot_percent`, the limit of power and the bed of the settings file, and a pilot power in the settings file is only a value shown in the box.
- **The focus test in the window:** a new mode, with the boxes of the `[focus]` section of the settings file, works the test out with the same function as `phoenix-laser focus` and draws its lines. Its power and speed obey the limits of the window, the step of the height has no default (the test is refused until it is given, because which way is down depends on the machine), a warning that the test moves Z stays in the notes, and the G-code is written with the same header as the command line.
- **A tone curve in the settings file:** the new `[tone]` section (`gamma`, `contrast`, `brightness`, `invert`, `auto_level`) is the starting point of `engrave --config`, under a material and the options `--gamma`, `--contrast`, `--brightness`, `--invert` and `--auto-level`, and the starting values of the boxes of the window.
- **Tone, materials and limits in the window:** the boxes of the tone curve (with switches for invert and auto level) work the picture out with the same function as the command line, so the window and `engrave` write the same G-code. A library of materials is loaded from a file or from `PHOENIX_LASER_MATERIALS`, and a material chosen from the list fills the boxes of the power, speed, dot, dithering and tone, and the table of layers of a drawing. The limits of power and of speed are boxes (they start from `[machine]`) and the window refuses a power, a speed or a grid over them, never lowering it. The words of all of this are in the eight languages.
- **Contours from a picture:** `phoenix-laser trace IMAGE OUT.nc --width-mm W` follows the outline of a logo, a silhouette or a stencil instead of burning it dot by dot. The grey levels are split at `--threshold` (ink under it, over it with `--invert`), the border is found with marching squares that place every crossing by the grey levels on both sides of it, the rings are simplified with the Douglas-Peucker rule until no point is farther than `--simplify` mm from the line, and rings smaller than `--min-area` mm2 are dropped. The result is a layer called `trace`, cut (or filled with lines with `--engrave`) with the settings of the file and the options of `cut`, with the same checks of the G-code. The new `[trace]` section holds the defaults and the limits (`max_pixels` reduces a big picture, `max_contours` and `max_segments` refuse a picture that is too detailed).

The profile that is chosen with `profile = NAME` in `[machine]` or with `--profile NAME` (on `engrave`, `calibrate`, `cut`, `vector`, `layers`, `focus`, `frame` and `preview`) is the machine: its values win over `[machine]` and the options of the command line win over both. A layer, a `--feed`, a `--feeds`, the frame or the focus test that asks for more is an error that names it, the way a power over the limit of power already is.
- **The cap of the pilot power of the frame is a setting:** `max_pilot_percent` in `[frame]` (5 by default, from 0 to 100; 0 allows no pilot power at all) replaces the fixed 5 %. The limit of power of the machine (`max_power_percent`) still holds over it, a `pilot_percent` above the cap is an error of the file, and `--confirm-laser-on` is still needed on every run.

## [0.0.7] - A tone curve, ordered dithering, a limit of power, a library of materials, a preview of the program, a frame with the laser off and a focus test

- **Focus test:** `phoenix-laser focus OUT.nc --z-step MM` writes a ladder of short lines side by side, each burnt with the head at another height, so that the sharpest and thinnest line shows where the beam is in focus; it goes back to the first height at the end. The step of the height has no default, because which way is down depends on the machine and a head sent the wrong way can hit the material; the power of the test obeys the limit of power. The usual values (first height, step, number of lines, length, spacing, feed, power) live in the new `[focus]` section of the settings file, and the output is never written over that file.
- **The strings of the tests of the limit of power and the frame are written on one line each,** the way the other tests of the settings file write them.
- **The frame of the work, with the laser off:** `phoenix-laser frame OUT.nc --size W,H` (from the corner `--origin`) or `--gcode PROGRAM.nc` (the box of what burns in a program, so its real place is framed) writes a program that traces the rectangle, `--margin` wider and `--laps` times, to see where the work will land on the material. The laser stays off: no power is set and the spindle is never turned on. A weak pilot power (`--pilot`, at most 5 % and at most the limit of power) needs the words `--confirm-laser-on` on every run, even when the settings file asks for it, and the program turns it off before it ends. A frame outside `--bed` is an error. The usual values live in the new `[frame]` section of the settings file (`feed_mm_min`, `laps`, `margin_mm`, `pilot_percent`).
- **Preview of a G-code program:** `phoenix-laser preview PROGRAM.nc [OUT.svg]` reads a program (this one's or another's; G0, G1, arcs as lines, millimetres or inches, absolute or relative) and prints its moves, the burnt and travelled length, the box of the work, the powers and a time that counts the speed and the braking at every corner (`--accel`, `--rapid`). It also warns of what looks dangerous: the laser on during a rapid move, a burning move with no feed, `S` above `--smax`, work outside `--bed` and a program that does not end. With an output file it draws the path as an SVG, the travel thin and dashed and the burn in a colour that deepens with the power. It only reads text, takes the machine from `--config`, and never writes over its program.
- **A library of materials:** a plain text file with a `[material NAME]` section for each material and way of working (power, speed, passes, focus step, beam width, hatch and, for a picture, dot size, overscan, dithering and tone curve). `--material NAME --materials FILE` (or `PHOENIX_LASER_MATERIALS`) applies one to `engrave`, `cut`, `vector` and `layers` under the options of the command line, `phoenix-laser materials FILE` lists a library, `examples/materials.cfg` shows every key, and the limit of power still holds over a material. A value out of range, an unknown key or a name used twice is an error that names the line, and the output is never written over the library.
- **A limit of power that refuses instead of lowering:** `max_power_percent` in `[machine]` (100 by default) and `--max-power` on `engrave`, `calibrate`, `cut` and `vector`. A program whose power is over the limit is an error that names the option or the layer, so what is written is always what was asked for. `engrave` and `calibrate` take `--config FILE` to read the limit and `s_max` from the `[machine]` section of the same settings file as the other commands, and never write their output over that file.
- **Ordered dithering (Bayer):** `engrave --dither bayer` decides every dot by its own place and grey with an 8 x 8 Bayer matrix, so the pattern is regular and a grey burns the same dots every time; it is also in the list of dithering methods of the window, in the eight languages.
- **Tone curve for a picture:** `engrave` takes `--gamma`, `--contrast`, `--brightness`, `--invert` and `--auto-level`, which change the grey levels with one table of 256 entries before the dots are made (`src/tone.rs`). The default values leave the picture exactly as it is, and a value out of range is an error that names it.
- **The README says the maturity of the manifest:** the badge and the Maturity row of the eight READMEs read functional, as the manifest does, and the check of the status lights now fails when they differ.
- **`engrave` and `calibrate` write their file the way `cut` does:** through a temporary file that replaces the output only when it is complete, so a full disk leaves no half program under the final name; `engrave` refuses an output that is the image it is made from; `--smax` of both takes a whole number only (1000.7 is an error instead of 1000).
- **A name in a comment of the G-code loses the characters GRBL obeys at once:** `!`, `~` and `?` become `_` in the layer names written to comments, as the common header already does.
- **No rapid move of the image or of the test grid travels with a power set:** the image writer and the grid write `S0` before a `G0` when the line before burned and nothing had put the power to zero (an image without overscan, the squares of the grid). Tested by reading the power in force at every rapid move.

## [0.0.4] - Vector cutting and engraving from SVG and DXF, the window with a table of layers and the Windows icon

- **Ready-made programs for every system:** the `Release binaries` workflow, started by hand by the owner from main, builds the window version for Windows (64 and 32 bits), Linux and macOS (Apple silicon and Intel), packs each with the licence, the README, the icon and the examples, writes the SHA-256 of every package, `SHA256SUMS` and a build manifest, attests their provenance, checks the result as a stranger would and, only when the dry run is switched off and the owner approves, prepares a draft release; the README has a Downloads section that tells how the signed packages are checked.
- **Vector drawings are read:** `svg` reads a safe subset of SVG (`path` with `M L H V C S Q T A Z` absolute and relative, `rect` with round corners, `circle`, `ellipse`, `line`, `polyline`, `polygon`, `transform`, groups, the layers of Inkscape, stroke and fill colours, the units `mm cm in pt pc px` with a settable `dpi`) and `dxf` reads `LINE`, `LWPOLYLINE` and `POLYLINE` with bulges, `ARC`, `CIRCLE` and `SPLINE` (through its fit points, or from its control points, knots and weights) with the unit of the file. Scripts, images, `use`, text, gradients and styles with selectors are never run or fetched and are skipped with a note; a declared entity is an error. Curves become straight pieces that stay within a settable tolerance of the true curve. The size of the file, the depth, the elements, the shapes, the points and the pieces of a curve are limited by settings.
- **Cutting and engraving by layer:** the shapes are grouped by colour (SVG) or layer (DXF); each group is cut or engraved with its own power, speed and passes. Cutting joins loose lines whose ends meet, cuts the contours that lie inside another one first and keeps the travel with the laser off short (the nearest next contour and then a limited 2-opt improvement that never breaks the inside-first rule), moves a closed contour half the width of the beam to the right side (outside a piece and inside a hole, or always one side) with round corners and a check of every edge of the result, leaves tabs uncut on the outline of a piece, and moves the focus on at each pass. Engraving fills closed shapes with lines at an angle and spacing (the even-odd rule, one way and then the other, with overscan) and follows open ones. A contour that is too small or too narrow for the beam is left out with a note instead of being cut wrong.
- **The settings are in a file:** the limits of the readers, how a file is read, the order of the cuts, the machine (full power, overscan, speed of the travel, origin, focus, bed) and the settings of each layer or colour are keys of a plain text file that is checked line by line (an unknown key or a value out of range is an error that names its line); nothing tuned is in the code. `docs/vector-settings.md` has every key with its default and its range, and `examples/plate.svg`, `examples/plate.dxf` and `examples/plate.cfg` show them at work.
- **A G-code that is checked before it is given:** the program of a drawing keeps the form of the one of a picture (`G21`, `G90`, `M4 S0`, `S0` while it travels, `M5` and `M2` at the end) and every line is checked: only the words the program writes, `S` never above full power, no laser on during a rapid move or a move of the focus, no cut without a speed, no move outside of the bed (when its size is given), and a power that rounds to `S0` is refused. A program that fails is not written. The file is never written over the drawing or the settings it is made from.
- **Commands `cut`, `vector` and `layers`:** `cut DRAWING OUT.nc` follows the contours, `vector DRAWING OUT.nc` fills the closed shapes with lines, and `layers DRAWING` lists the layers with what would be done with each; they take `--config FILE` and the options `--power`, `--speed`, `--passes`, `--focus-step`, `--kerf`, `--kerf-side`, `--tabs`, `--tab-width`, `--angle`, `--spacing`, `--smax`, `--overscan`, `--origin`, `--bed`, `--dpi` and `--tolerance` over the settings of every layer, and `--dry-run` works the job out without writing.
- **The window opens drawings:** an SVG or a DXF is opened from the list of files or dropped on the window and the program switches to cutting; the path of the laser is drawn with the cut in one colour and the travel dim, the table of layers (mode, power, speed, passes, step of the focus, width of the beam and its side, tabs, hatch angle and spacing) is edited in the window, a settings file can be loaded, the notes of the reading and of the plan are listed, the time is estimated and the G-code is exported with the same header as the one of a picture. The words are in the eight languages.
- **A window:** built with `--features gui`, `phoenix-laser` with no arguments (or with one picture, or `gui [IMAGE]`) opens a window in the look of the other programs of the suite (amber on charcoal, the icon of the program). A PNG or PGM picture is opened from the list of files of the window or dropped on it; the passes of the laser are drawn as the head makes them (burning in a colour that follows the power, travel and overscan thin), with zoom (wheel) and pan (drag); the width, the size of a dot, the dithering and its threshold, the feed, the power, the full power value, the overscan (typed or worked out from the acceleration) and the origin can be edited, a calibration grid of power against feed can be made, and the G-code is exported with the same header as the command line. The command line works as before, and a build without the feature is only a command line.
- **The window speaks the eight languages:** English, Spanish, German, French, Italian, Japanese, Chinese and Portuguese of Portugal, chosen from the system and changeable in the window.
- **The logic of the window needs no screen:** `window` (picture, settings, engraving, passes, export, status), `viewport` (zoom and pan), `browse` (the list of files) and `lang` (the words) are plain code with their own tests; `gui` only draws them.
- **The Rust version needed is 1.88,** the one the window needs.

- **Renamed:** The project is now called EH3D-PHOENIX-LASER (it was EH3D-LASER-CAM); it joins the PHOENIX family of programs.

## [0.0.3] - Audit fixes, the new reading limits, tests and the application icon

- **The application icon and the logos of the program:** `images/brand/` holds the icon (SVG, PNG sizes, `.ico` and `.icns`), the horizontal and vertical logos in a light and a dark version and the social preview image.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **Every G-code file opens with a standard header:** comment lines with the generator and its version, the units (mm, G21), the picture it was made from with its SHA-256 and the tools (the laser and its power); the calibration grid says it has no source. The library functions keep returning the program alone, so the header belongs to the files the command line writes.
- **One way to write a number, and no `NaN` or `inf` in a file:** the engraving and the calibration grid write every number with the same function (`gcode_out::number`: three decimals at most, no `-0`), and a value that is not finite is an error. The SHA-256 used by the header is written in the program itself (no new dependency) and checked against the known test vectors.
- **The reader of pictures comes from EH3D-COMMON (`eh3d-image`):** the program no longer keeps its own copy of the PGM and PNG reader; it takes it by path from the sibling repository, which must be cloned beside this one. `eh3d_*::image` keeps working as before. The manifest names EH3D-COMMON in `depends_on` and the CI checks it out.
- **More tests:** the G-code read back into the dots it was made from, the limits of the head and of every value, the calibration grid square by square, and the command line with its errors and file names in any script.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, and the checkouts keep no credentials.
- **More tests of the limits:** every value of the parameters at its edges, what the engraving reports, and the shape of the lines at the ends.

## [0.0.2] - Dry run for engraving

- **Strict command line:** an option that is written wrong (`--powr`) or a word too many is an error that names it; before, it was ignored and the output was made with the default values.
- **A dot size that makes no sense is refused before anything is reserved:** `--dot-mm 0` or a tiny one, or an image that would be larger than the limit, gives an error instead of an allocation failure or an overflow.
- **`engrave --dry-run`:** works the engraving out and counts it (dots, lines, runs, burnt length, time), without writing the output file (which may then be left out).
- **One shared helper for the command-line arguments** (`src/cli_args.rs`: flag, switch, num and a strict finish), the same file in every small utility of the suite; the copies this program had behaved the same, so nothing changes for a person.
- **Tests that run what the README and the scripts promise:** the sample of `run.sh`, `run.bat` and the README is the same command, and it is run on the files of `examples/`.
- **The banner of the README** shows the role and the technologies of this program (it showed the text of the shared library).

## [0.0.1] - An image engraved by a laser: dithering, raster G-code with dynamic power and a calibration grid

- **The image:** PNG (grey, colour, transparent, 8 or 16 bits) and PGM, with the size limited; `resize` averages the pixels.
- **The dots:** threshold, Floyd-Steinberg and Atkinson, checked to keep the darkness of a grey.
- **The laser:** `M4` with `S0` while it travels, alternating directions, an overscan fixed or worked out from the acceleration, and the top of the image as the highest Y.
- **The calibration grid:** a square for every pair of a power and a feed.
- **The command line** `eh3d-lasercam` with `engrave`, `calibrate` and `info`, and a sample gradient.
- **18 tests** run on a computer, with damaged input.

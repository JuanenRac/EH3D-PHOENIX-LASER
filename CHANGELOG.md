# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Safety, the check reads a program the way the controller does:** spaces inside a line count for nothing, so a power written `S1 000` is judged as `S1000` and `X1 000` as a metre. Before, only the part up to the space was read, and a power over the limit or work outside the bed could pass.
- **Safety, a danger is never lost behind other notes:** what makes a program fail (the laser on during a rapid move, a burning move with no feed and the rest) is kept apart from the ordinary notes. Before, twenty earlier notes filled the list and a later danger was dropped, so the program passed.
- **Safety, a program too long to be read whole fails:** the check says that the rest was not looked at instead of passing it.
- **Safety, constant power left on while the head stands fails:** with `M3` and a power above zero, a wait (`G4`), a pause (`M0`, `M1`), a move of the height only, or the end of the program with no `M5`, `M2` or `M30`.
- **Safety, a command of the controller inside a program fails:** a line with `$` can write a setting (the laser mode among them), unlock an alarm or move the head.
- **Safety, what cannot be judged fails:** a part of a line that is not a letter with a number (it was left out without a word), `G93` and `G95`, the M codes that other controllers use to switch a laser (`M106`, `M67` and others), and a power or a feed below zero. An M code that GRBL does not know is told.
- **Safety, characters the controller obeys at once:** `!`, `~`, `?`, control characters and characters outside of ASCII fail in the code and are told in a comment; a line longer than GRBL takes is told.
- **Settings of the controller:** `phoenix-laser controller` reads a saved answer to `$$` and says in the eight languages what does not agree with the machine (laser mode off or unknown, full power `$30`, least power, inches, travel); `verify --controller` adds it to the verdict. Nothing is sent to a machine and the listings tried were written for the tests.
- **Alarms and errors:** `phoenix-laser explain ALARM:n|error:n` says in the eight languages what the common ones of GRBL mean.
- **Test of the spacing of the lines:** `phoenix-laser interval` writes a row of squares filled at different spacings, with the figures below, and only when it passes the check.
- **Test of the width of the beam:** `phoenix-laser kerf` writes a rectangle cut into strips, and `kerf --gap` gives the width of the beam from the gap measured.
- **Four more ways of dithering:** Jarvis, Stucki, Sierra and Burkes, on the command line, in the library of materials and in the window.
- **A line that would be cut twice is told:** pieces drawn twice in a layer that is cut are counted in the warnings, since they put twice the energy in one place.
- **A project saved by another program is not written over:** the window keeps the mark of the project from the moment it opens or saves it, looks at it again after a question, and refuses to save, import or take when another program wrote the file meanwhile. It says so in the eight languages and offers to read it again, to save under another name or to close. 3 new tests.
- **What the tag v0.3.7 of EH3D-COMMON brings to the window:** the panel «Attachments» refuses the same writes and reads its list again, and `viewer.max_preview_mb` (16 by default) in the settings says how much text a whole preview keeps.

- **The top bar takes a second row in a narrow window:** under about 1000 points of width the buttons lay over the box of the language, which was cut at the edge; what does not fit now goes to a further row.
- **The key of the powers no longer lies over the preview of an engraving:** in a low window the key was drawn on top of the picture; it now has its own strip over the preview, the work is fitted and clipped under it, and in a low panel the key takes a single row. A test draws the preview with no screen at several sizes.

- **Escape answers no to the question before a project is written:** the question that the window asks before a write removes a signature (or replaces a branch it did not write) closes with Escape without writing, and Enter does not write; the commands do not ask.

The packages carry the PDF library (PDFium) and its licences.

Amber text is left for cautions only (values that were not tried on a machine); the colours of the drawing and of the path keep their meaning.

A project is a file that is passed on; one saved before with such a file should be looked at and the token changed.

- **The `.eh3d` project from the menu File of the window (`docs/eh3d-project.md`):** a submenu opens a project, saves it and saves it under another name keeping every branch, imports a drawing keeping the original, takes a file of another branch, extracts a branch and lists the branches, with the same functions as `phoenix-laser project`. What is out of date and what is signed stays in sight, and the window asks before it writes a project that was not opened there, a branch that changed since it was read or one whose signature the write removes. Opening a project never loosens the limits, the interlocks or the server of the person's settings, and a settings file with the token of the server is not put into a project.
- **The branch `laser/` is handled by the module of the suite that every program shares:** the commands of `phoenix-laser project` behave as before; in addition `list` says when a branch is signed, and a change says when it removes the signature of the branch.
- **A new window «About»:** the picture of the program inside a ring of its colour (red), the name in large letters, one sentence about the program in the eight languages, the version, the author and the e-mail, links to the page of the author and to the repository and the licence. It is the window of the docking frame of the suite (`eh3d-dock`), so the workflows build against `EH3D-COMMON` at `main` until a release of it carries the window.
- **The work can live in the branch `laser/` of an `.eh3d` project (`phoenix-laser project list|save|import|open|take|extract`, `docs/eh3d-project.md`):** `save` puts the drawing, the settings, the materials and the programs there, `import` keeps an LBRN2, LBRN, SVG or DXF file of another program byte for byte with a report of the conversion, `take` copies an outline or a mesh of another branch with a reference that tells when it is out of date, and every other branch keeps its bytes. A branch of a newer format or a sealed one is not written. The build now needs the project crates of EH3D-COMMON.
- **The checks of power and speed, the gate before a vector job leaves and the percent of a job are stricter:** a negative power or speed passed `check_power` and `check_speed`; a vector job with a power or speed that was not a number, a negative power, a speed of 0 or less, or a point that was not a number was sent when no bed was set (a comparison with a number that is not a number is never true); the percent of a job overflowed when the server answered a huge count of lines. 43 new tests keep them, and cover the ids that go into a request, the forbidden zones at their edges and the energy of a layer.

## [0.1.6] - Hatch and legacy project reading, power and speed matrix and Y axis test projects, project layers as settings, preset book as text

- **LBRN2 projects are read:** `cut`, `vector`, `layers` and `convert` (and the window, by opening or dropping the file) take a `.lbrn2` project in place of an SVG or a DXF. The rectangles (centred on their origin, with a corner radius), the paths (lines and cubic Bezier pieces, with the handle that leaves the first vertex and the one that arrives at the second, the `LineClosed` shorthand, and the lists a path leaves out because an earlier path wrote them), the groups with their transforms at any depth and the outline of a text (from its backup path, with the transform applied once) become a drawing in millimetres, with the curves cut within the tolerance of `[read]`. The format has no published specification, so it is read from the behaviour of real files; a shape of a type that was not seen, a text with no outline, a path whose lists are missing and a shape whose transform is not six numbers are left out with a note and counted, never drawn in a wrong place. The limits of `[limits]` hold (size, depth, number of elements, shapes, points, coordinates), a declared entity is an error, and the y axis is taken as the one of an SVG (not confirmed on a machine). Written in `src/lbrn2.rs` and described in `docs/lbrn2.md`.

- **The layers of a project fill the table of layers:** the power, the speed (the project has mm/s, the table mm/min), the passes, the distance between the lines of a fill and the order of each layer of an opened project are the values of its row, a layer that is not sent to the laser is skipped, and a layer that the settings file names keeps what the settings file says. They are hints: the limits of the machine hold over them when the work is made, so a power over the limit is an error that names the layer and is never lowered, and the notes of the drawing say that the values are the project's and have to be checked for the machine.

- **A tool that reads a folder of projects and says what the reader leaves out:** `cargo run --release --example lbrn2_survey -- FOLDER [--out REPORT.txt]` reads every `.lbrn2` file under a folder with the reader of the program and reports, for each, whether it was read and why not, the version and the size of the drawing, the number of shapes, curves and shared lists, the notes, and what was left out; at the end it lists the shape types seen and the elements and attributes the files hold that the reader does not use (`inventory` in `src/lbrn2.rs`). It only reads the files, copies none, and exits with 2 when a file is not read. The reader was measured on twelve real projects of one laser maker (kept outside this repository): all twelve are read, in 34 ms or less each, and the one picture among them is left out.

- **The window is the docking frame of the suite:** the window of the program (`--features gui`) is laid out with `eh3d-dock`: twelve panels (view, layers, settings of the work, properties, library, materials, framing, machine, simulation and time, job, report and console) that can be taken away, put back, moved, tabbed, floated, folded into an edge and maximised, each one the contents of what used to be the side panel, the table of layers, the picture and the sections of the server and the preview. The panels, the workspaces, the menus and which entries can be chosen at a moment are plain data in `src/panels.rs`, with tests, and the drawing in `src/gui.rs` only does what they say.

- **Four workspaces for tasks, never for levels of experience:** Prepare (the file, the materials, the view with the layers, the settings and the job), Run (the view, the job, the machine, the framing, the simulation and the console), Review (the view with the layers, the report, the simulation and the settings) and Compact (the view and the job, the rest folded into the edges); their names are shown in the eight languages. Every setting is in the same panels in all of them, and `--shot ... --window prepare|run|review|compact` takes a picture of each.

- **A menu bar:** File (open a picture or a drawing, a file of settings, a G-code program or a library of materials, make a new library, export the G-code, quit), Edit (the entries of the suite, off because the program has nothing to undo), View (one check mark for each panel, restore and lock the layout), Tools (work it out with F5, fit, make the report, send to the server, stop with F12), Window (the workspaces, save the layout under a name) and Help (the shortcuts and the window about the program).

- **The stop of the job and the state of the interlocks are outside every panel:** a bar at the bottom of the window, in every workspace and in the compact one too, holds the stop of the job that was sent to the server and one line with the emergency stop, the cover and the air assist of the settings file in the language of the window (in red when the stop is pressed or a required interlock is not safe). They are not panels, so no layout can hide, float or fold them away; the interlocks are still simulated, nothing here reads a sensor.

- **The report is made in the window:** the report of `phoenix-laser report` (the file and its SHA-256, the moves, the box, the power and the speed against the limits, the energy, the material, the zones, the interlocks and the verdict) can be made from the program the window has worked out, in the language of the window, and it is dropped when anything changes.

- **The arrangement of the panels is kept in the settings file:** the window reads it at the start and writes it back, as lines that start with `dock.`, when it changes (a few times a second at most, and never in the picture mode or without a settings file); every other line of the file stays as it is, and the reader of the settings leaves the `dock.` lines alone wherever they are while a line that is not a setting is still an error. A damaged or foreign arrangement is repaired or replaced by the factory one and never stops the program.

- **Starting points from the common database of materials, as they are:** the new feature `common-machining` takes the family of workpieces of `eh3d-materials` (its `machining` module) and the panel of materials gives, for a material, a kind of laser (diode or CO2), cut or engrave, the power of the laser in watts and the thickness, the power, the speed and the passes that the database has, with no figure added here. The note that nobody tried the point on a machine is always in sight in the language of the window, a material that must not meet a laser is refused with the reasons the database gives, a value outside the known range has no answer (nothing is extrapolated), and the values go into the boxes and the table as a material marked as not verified, under the limits of the machine. The feature is on by default now that the release of the common repository this program is built against (0.3.0) has the module; `--no-default-features` leaves it out, and the CI checks that build too.

- **The CI builds against the common library at its release 0.3.0:** the workflows name the tag of each sibling repository in one place (`SIBLING_REFS`), and the checkout of the siblings reads it.

- **The pictures of a project are engraved:** the `Data` of a picture of an LBRN2 project (base64 text of a PNG, or of a PGM) is decoded within new limits, `max_bitmap_bytes`, `max_bitmap_pixels` and `max_bitmaps` of `[limits]` (the pixels the picture claims are read from its header before anything is unpacked), turned and mirrored as its transform places it (a flip and a quarter turn) and kept. `phoenix-laser engrave PROJECT.lbrn2 OUT.nc` engraves it by dots with every option of `engrave`: `--picture N` takes the Nth picture, the width and the proportions of the project are used when `--width-mm` is left out, and the power and the speed of the layer of the picture are used when the command line gives none (a value over the limit is refused, never lowered). A picture that is too long, has too many pixels, is one too many, is in a format the program does not decode (a JPEG), is damaged or is turned by something other than a quarter turn is left out with a note that carries a stable code (`PHOENIX-LASER-LBRN2-BITMAP-SIZE`, `-PIXELS`, `-COUNT`, `-FORMAT`, `-DATA` and `-ROTATED`). Only one of the twelve real projects held a picture, so this is tested on pictures made for the tests.

- **The direction of the y axis of a project is a setting, and every reading says it is not confirmed:** `lbrn2_flip_y` of `[read]` (on by default, which is what the program always did) takes the y axis of a project as pointing down like the one of an SVG, and `off` takes it as pointing up like the one of the machine. Whichever it is, the notes of every reading that holds a drawing or a picture say which direction was used and that it was never confirmed with a real part, so the report before a job and the window carry the warning.

- **An ellipse, a polygon, the tabs of a layer and the counter of the variable text of a project are read (prototype):** an `Ellipse` (the radii `Rx` and `Ry`, or one radius `R`) and a `Polygon` (`N` sides on the ellipse) are drawn from the names of their attributes alone, because no real project had one; a layer that cuts and has `tabsEnabled` on gives the table of layers its `tabCount` tabs of `tabSize` millimetres as hints; and the `VariableText` block (`Start`, `End`, `Current`, `Increment`) is read as a counter. A shape of any other type is still left out with a note.

- **Variable text from a CSV file or a counter:** `phoenix-laser text OUT.nc --text 'N{counter:4} {name}' --csv FILE.csv` writes one program for each row (`OUT_001.nc`, `OUT_002.nc`...), where `{counter}` and `{counter:5}` (five figures), `{row}` and `{NAME}` (a column of the first row of the file) are the places of the text and `{{` and `}}` are the braces. `--counter START,STEP,COUNT` gives the counter (the rows of the file when there is one) and `--counter-project PROJECT.lbrn2` takes it from the variable text of a project; `--preview` shows the text of every row and writes nothing. Nothing in a CSV file is ever run, a place that names nothing is an error, the file is held to `max_csv_bytes`, `max_csv_rows` and `max_csv_columns` of `[limits]`, and every program is worked out and checked before the first one is written, so a row that cannot be burnt (a character the font has not, a power over the limit) stops the whole series.

- **Sub-layers, several passes over a layer:** a `[sublayer LAYER/LABEL]` section of the settings file adds a pass over the shapes of a layer, with its own mode, power, speed, passes, focus step and hatch; it starts from the settings of its layer, is held by the limits of the machine like a layer (an error names the layer and the label, and nothing is lowered in silence) and is written under its own comment. The work goes engraving first and cutting last, each kind by its `order`, and a pass never goes before its own layer when the rest is equal, so a fill and an outline of one layer come out in that order. `layers` lists the passes with their time, a layer that is skipped takes its passes with it, and the server is told that its vector job carries the layers only.
- **Where the work goes, its frame and its time:** the new `[job]` section places the work by one of the nine points of its box (`anchor`, the lower left corner as before) at the origin of the machine, and `align = page` keeps the drawing where it was drawn. The frame of the work is its box with the margin of `[frame]`, written with the laser off and refused when it would leave the bed. The time is a range, from every move at its own feed with no braking to the time of the preview with the braking at every corner at `accel_mm_s2`, with the passes in both and a time for each pass.
- **Presets that are assigned or linked:** a preset of a material and a thickness is copied into a layer (assign) or tied to it (link), and a change of a linked preset reaches its layers and says which; a change that any of them cannot take is refused as a whole, and a value over a limit of the machine is an error that names the preset and the layer. The values of the common database are used exactly as given and marked as not tried on a machine, with the warning in the eight languages, and the second figures of other sources are kept apart and are not used unless they are asked for. The links are kept in memory for now.
- **The live adjustment of power and speed, held by four limits:** a calculation, with the new `[live]` section for its range (it never raises a value by default), that gives the value to use for a percent that is asked and is held by the range, the limit of the machine, the limit sent to the server and, for the pilot, the limit of the pilot; a value that was held says which limit held it in the eight languages. Nothing is sent to a machine.
- **The outline of a DXF hatch and of a solid is drawn:** a `HATCH` gives one closed shape for each of its boundary paths (a polyline path, or edges that are lines and arcs of a circle chained one after the other, in either direction), a `SOLID` or a `TRACE` gives its three or four corners in the order that goes round them, both also inside a block that an `INSERT` places. The fill pattern of a hatch is not drawn, an edge that is an ellipse or a spline is skipped, and each of these is said in a note; a hatch with nothing to read still says so. Damaged hatches are read with a fixed seed and never stop the reader.

- **Projects of the older format (`.lbrn`) are read:** a path written as one `V` element for each vertex (with its handles) and one `P` element for each piece (a line or a curve) is drawn like the lists of text of a `.lbrn2` project, and the extension `.lbrn` is taken by `cut`, `vector`, `layers`, `convert`, `engrave`, the window (the list of files, opening and dropping) and the notes of the reader. The inventory counts `V` and `P` as read. Paths with a vertex without its coordinates, without pieces, with a piece outside its vertices or of another kind are skipped with a note, and damaged projects are fuzzed with a fixed seed.

- **The text of an older project is drawn with the stroke font:** a `Text` that has only its letters (`Str`) and its height (`H`), as the older format writes it, is drawn with the font of strokes of the program in capitals, placed by `Ah` (left, centre, right) and `Av` (top, middle, bottom) from the point of its transform. That is a guess at the shape and the place, and the notes say so; a character that the font has not is left blank and said, and a text with nothing to draw or a height over the limit of the font is counted as left out.

- **The layers of a project give the command line their values:** `--project-layers` of `cut`, `vector` and `layers` gives each layer of an `.lbrn2` or `.lbrn` project the power, the speed (mm/s of the project, mm/min here) and the passes of its row, as the window does; a layer that the settings file names keeps what the file says, `--material` and the options of the command line still win, and the limits of the machine hold over all of them. The command says how many layers it took.

- **Ranges in the lists of a test grid:** `--powers` and `--feeds` of `calibrate` (and `--powers` of `focus`) take a range `FIRST:LAST:STEP` beside plain numbers, so `20:80:20` is 20, 40, 60 and 80; the values are rounded to six places, a step that does not reach the last value stops below it, a series holds at most 1000 values, and a range that is wrong (no step, a step of 0 or below, a last value below the first, not a number) is an error that names the option. Random ranges are checked with a fixed seed.

- **The power-against-speed matrix as a project:** `phoenix-laser matrix OUT.lbrn2 --powers 20:80:20 --feeds 600:2400:600` writes a square for every pair on a layer of its own, named after the pair (`P40 F1200`), filled with lines or only outlined with `--outline`, with the size and the gap of `--square-mm` and `--gap-mm`; the program or any other that opens the project shows what each square was meant to be, and the layers reach the table of layers with their power and speed. Nothing outside of 1 to 12 powers and feeds, a power from above 0 to 100 percent and a feed from 1 to 30000 mm/min is written. Read back exactly, with random matrices of a fixed seed.

- **A project that shows which way the y axis points:** `phoenix-laser ytest OUT.lbrn2` writes a square, a rectangle and an arrow whose point is at the larger y of the file, on one weak layer. Which way the y axis of a project points depends on the program that wrote it, so the file is for opening in the program that made the projects you have: where the arrow points tells what to set `lbrn2_flip_y` of `[read]` to. The test shows that the setting turns what the reader sees; it settles nothing until a person looks at it or burns it.

- **A book of presets kept as text:** the presets and the layers they are assigned or linked to are written by `Book::to_text` (a `[preset NAME]` section for each preset, a `[bind LAYER]` or `[bind LAYER/LABEL]` section for each binding, always the same text for the same book) and read back by `Book::from_text` as they were, held to 1 MiB, to the keys each section knows, to a key once, to the checks of a preset and to a binding that names a preset of the book and its target once; a mistake names its line and nothing of a damaged text is kept. `phoenix-laser presets BOOK.cfg [--lang CODE]` lists a book in one of the eight languages, with the warning of every preset that was not tried. Random books are written, read back and damaged with a fixed seed.

- **The readers can be tried on a folder of samples:** the variable `PHOENIX_LASER_SAMPLES` names a folder, and the new test reads every SVG, DXF, `.lbrn` and `.lbrn2` file under it within the default limits, asking for shapes whose points are numbers; without the variable it passes at once, so nothing in the repository depends on files of other makers.

- **Tests:** the suite has 986 tests, with the new ones for the extra passes of a layer, the nine anchors, the frame and the time, the presets and the live adjustment (damaged files and random series with a fixed seed), for the LBRN2 reader on projects written for the purpose (pictures in base64 with their flips, quarter turns and limits, the direction of the y axis, ellipses, polygons, tabs, the counter of the variable text, shapes, curves, handles, shared lists, groups and their order, text, pictures, hostile and damaged files, a fuzz with a fixed seed), for the layers a project gives, the report, the line of the interlocks, the arrangement kept next to the settings, the panels and the menus, and the starting points of the common database; for the variable text (CSV files, places, counters, series that stop at the first row that cannot be burnt, a fuzz with a fixed seed); and for pictures that are damaged, cut short or claim a size they do not have; and, with fixed seeds, for the hatches and solids of a DXF, the paths and the texts of the older project format, the ranges and the matrix of the test grid, the project of the y axis, the book of presets written, read and damaged, and the folder of samples.
- **Requirements with identifiers and tests that name them:** `docs/REQUIREMENTS.md` is the register of what the program must do, one row for each capability with an identifier (`PLAS-001` on), its state (planned, prototype, implemented or validated), how far it is (done, partial, pending or blocked), its evidence and the test that shows it; a capability that is not written names the test that will show it. `tests/reqs.rs` reads the table and fails when a test does not exist, when a state does not agree with the progress or the evidence, when `docs/STATUS.md` does not say the same numbers, when a README does not link the documents or when a document holds a date or a private reference. The five documents of the family (`docs/SCOPE.md`, `docs/REQUIREMENTS.md`, `docs/STATUS.md`, `docs/NOT_YET.md` and `AGENTS.md`) are in the repository and are linked from the eight READMEs.
- **The READMEs say what the program does today:** the honesty check, the safety note, the state of the window, the known limits and the next steps no longer repeat each other or mix states (nothing has run on a real laser, the window has not been looked at on a screen by a person, the server is a stand-in), the duplicated sentence about the server panel is gone, the note on the releases is true, and the file tree describes the calibration, dithering and raster modules and the extra test files.

## [0.1.5] - Forbidden zones and simulated interlocks, a 40 percent power ceiling for the server, arcs in G-code, DXF blocks, drawing conversion and a report before a job

- **The settings of the program as a contract:** `phoenix-laser settings [--json]` lists every setting of the program (the keys of the settings file and of a library of materials: section, key, the kind of value, the default and whether it is a safety setting such as a limit, a zone, an interlock or the token of the server), as lines of text or as JSON for a server, a studio or a test to read, so that every switch and number of the program has an entry that can be shown or checked without reading its code. Tests keep the list equal to the keys the reader takes (a key added to one and not to the other fails), every default that is a value is accepted by the reader and equal to the documentation, and the JSON reads back.

- **A report to read before a job, in eight languages:** `phoenix-laser report PROGRAM.nc [--lang en|es|de|fr|it|ja|zh|pt]` writes the check of `verify` as something to read before the program is started: the SHA-256 of the file, the moves, the length burnt and the time, the box of the work, the highest power and speed against the limits, the energy when the power of the laser is set, whether the material of `--material` was verified (or never said), how many forbidden zones were checked, what the interlocks of the settings say, the reasons of a failure and a verdict that says plainly not to run a program that fails. The words are in the language asked for (the one of the system by default; Portuguese of Portugal for `pt`); the reasons that the check gives stay in English, as it writes them, and say so. It reads the file as text, runs nothing, and ends with code 1 when the program fails. A test checks that every text exists in the eight languages with the same places for its values.

- **Drawings written as SVG or DXF:** `phoenix-laser convert DRAWING OUT.svg|dxf` reads a drawing (an SVG or a DXF, with its curves cut into straight pieces within `--tolerance`) and writes it again as a plain SVG (one group for each layer named as Inkscape names its layers, a `polygon` for a closed shape and a `polyline` for an open one, in millimetres with the y axis down) or as the old ASCII DXF of release 12 (`POLYLINE`, `VERTEX` and `SEQEND`, a table of layers, in millimetres, with the colour as the AutoCAD index when it is one of the nine basic ones and always as a true colour), so another program can open what this one understood. The extension of the output chooses the format, a drawing is never written over itself, a drawing with no shape is an error, and the layer names the old form does not allow are written with `_`. The tests read every file back with the program's own readers.

- **DXF drawings with blocks and ellipses:** the DXF reader now draws `INSERT` (a block of the `BLOCKS` section at its insertion point, scale and rotation, with its base point, as an array of columns and rows too, a block inside a block, and an extrusion pointing down), and `ELLIPSE` (a whole one or an arc of it, cut into pieces within the tolerance of the reader). The entities of a block that are on layer 0, or have no colour, take the layer and the colour of the `INSERT`, the insertion point is in the unit of the file, and what a block adds counts against the limit of entities, how deep blocks nest is limited by `max_depth` (a block that draws itself is an error, not a loop) and an `INSERT` of a block the file does not define, or with a scale of 0, is skipped with a note. Before, both were skipped.

- **What is sent to the server is held to 40 % of the power by default:** the laser plugin of the server is a simulator that refuses more than 40 % of full power until its own limit is changed, so the program now holds a program, a vector job and a test fire to the lower of the limit of the machine and the new `max_power_percent` of a `[send]` section (40 unless the file says another, from 0.1 to 100) before anything leaves, and says which of the two limits it was; a drawing that asks for more says so by layer. Nothing local changes: the engraving, the cutting and the other commands keep the limit of the machine alone.

- **The ceiling of a material holds over the command line:** `engrave` and `cut` refuse a power or a speed (from the library, from `--config` or from `--power` and `--speed`) that is over the `max_power` or `max_speed` of the material in use and say which layer asked for it, and the ladder of `calibrate --material` is held below that ceiling as well as below the limits of the machine; nothing is lowered quietly.

- **Materials say whether they were verified and how far they may be pushed:** a material of a library can carry `verified` (`off` says its values are only a place to start from), `max_power` and `max_speed`, its own ceiling. A library whose `power` or `speed` is over the ceiling of its own material is refused when it is read, the list of `phoenix-laser materials` marks each entry `[verified]` or `[not verified]` (an entry that says nothing is left unmarked, as before), using a material that is `verified = off` prints a note on the error output to try it on a scrap first, the marks are written back and kept when a material is edited in the window, and the file keeps what it says when it is rewritten.

- **A starter library of materials:** `examples/materials-starter.cfg` holds seven places to start from for a weak diode laser (plywood cut, engraved and as a picture, cardboard, paper, leather and black acrylic), every one marked `verified = off` with a ceiling of its own and a note on what to watch; the values are round numbers from general experience, not copied from any table, and nobody has tried them on a real machine.

- **Forbidden zones of the bed:** a `[zone NAME]` section of the settings file (`x_mm`, `y_mm`, `width_mm`, `height_mm` and `kind`) names a rectangle, in millimetres of the machine, where the beam must not burn (`no_burn`: the head may cross it with the laser off) or where the head must not go at all (`no_go`, which a zone has when its kind is not said). A program that reaches a zone fails `phoenix-laser verify` (with the zone, how many moves reach it and the line of the first), the check of the window and the check before a program is sent to the server, and a drawing sent as a vector job is refused when one of its paths reaches a zone of either kind; the edges of a zone count as inside, the arcs of a program are checked along the curve, and a zone with no size, a name that is empty, a number that is not one or more than 64 zones are refused when the file is read. The report of `verify --json` lists `forbidden_zones` among its checks when there are zones.

- **Interlocks held in the settings file:** an `[interlocks]` section (`estop` as `released` or `pressed`, `enclosure` as `closed`, `open` or `unknown`, `air_assist` as `on`, `off` or `unknown`, and `require_enclosure` and `require_air_assist`) says what the machine is doing, because this program reads no sensor: a simulator, a gateway or the person writes it. A pressed emergency stop, and a required interlock that is not in its safe state (a state that is not known counts as unsafe), fail `verify`, stop the program, the vector job and the test fire from being sent, and say why; with the defaults (nothing required, the stop released) nothing changes, and the report lists `interlocks` among its checks only when they are active. Nothing here has been tried against a real sensor or a real emergency stop.

- **`G92` moves the origin in the reading of a program:** a program that says `G92 X0 Y0` (the head stays where it is and the program calls that place 0, 0) is read in the places where the head really goes, so the box, the burnt length and the check against the bed (`preview`, `verify`, the check before a program is sent) are no longer worked out from the numbers of the program alone; `G92.1` and `G92.2` take the name back, and a line with `G92` is not counted as a move. The words that choose other coordinates in the controller (`G10`, `G28`, `G30`, `G53`, `G54` to `G59.3`) are told in the notes, because there the places of the report are the ones the program writes.

- **The arcs of a program are drawn as arcs:** a program with `G2` and `G3` (in the form with the centre `I`, `J`, in the form with the radius `R`, and as a full circle when the end is left out) is cut into straight pieces no farther than `arc_tolerance_mm` of `[verify]` (0.01 mm unless the file says another, from 0.0005 to 1) from the true arc, so that the length, the time, the energy, the box and the check against the bed of `preview`, `verify`, `frame --gcode` and the check before a program is sent follow the real curve, which can reach past the bed where its two ends do not (before, an arc was counted as a straight line to its end). The centre as a point (`G90.1`) and the plane of the arcs (`G17`, an arc in `G18` or `G19` is told and drawn straight) are read, an arc whose two ends are not at the same distance from its centre is told like GRBL refuses it, a radius too short for its ends is told, and `G90.1` and `G91.1` no longer count as `G90` and `G91` (the way the moves are positioned).

- **A picture of any window of the program:** `--window NAME` with `--shot` shows one window of the program in the picture: one of its modes (`engrave`, `calibrate`, `cut`, `focus`, `frame`, `preview`, `trace`, `text`, `qr`, `marks`, `barcode`) is chosen, or `server` holds the section for the server open, which is how the panel of the server of the window is photographed for the README. The name is read in any case, a name the window does not have is refused with the list of names, and `--window` without `--shot` is refused like the other options of the picture; the picture still keeps no settings. The reading of the name is tested without a screen.

- **The pictures of the window are taken again with the newest build:** the two pictures of `images/screens/` come from the Windows 64 bits program of the latest release.

Engraving fills closed shapes with lines at an angle and spacing (the even-odd rule, one way and then the other, with overscan) and follows open ones. A contour that is too small or too narrow for the beam is left out with a note instead of being cut wrong.
- **The settings are in a file:** the limits of the readers, how a file is read, the order of the cuts, the machine (full power, overscan, speed of the travel, origin, focus, bed) and the settings of each layer or colour are keys of a plain text file that is checked line by line (an unknown key or a value out of range is an error that names its line); nothing tuned is in the code. `docs/vector-settings.md` has every key with its default and its range, and `examples/plate.svg`, `examples/plate.dxf` and `examples/plate.cfg` show them at work.
- **A G-code that is checked before it is given:** the program of a drawing keeps the form of the one of a picture (`G21`, `G90`, `M4 S0`, `S0` while it travels, `M5` and `M2` at the end) and every line is checked: only the words the program writes, `S` never above full power, no laser on during a rapid move or a move of the focus, no cut without a speed, no move outside of the bed (when its size is given), and a power that rounds to `S0` is refused. A program that fails is not written. The file is never written over the drawing or the settings it is made from.
- **Commands `cut`, `vector` and `layers`:** `cut DRAWING OUT.nc` follows the contours, `vector DRAWING OUT.nc` fills the closed shapes with lines, and `layers DRAWING` lists the layers with what would be done with each; they take `--config FILE` and the options `--power`, `--speed`, `--passes`, `--focus-step`, `--kerf`, `--kerf-side`, `--tabs`, `--tab-width`, `--angle`, `--spacing`, `--smax`, `--overscan`, `--origin`, `--bed`, `--dpi` and `--tolerance` over the settings of every layer, and `--dry-run` works the job out without writing.
- **The window opens drawings:** an SVG or a DXF is opened from the list of files or dropped on the window and the program switches to cutting; the path of the laser is drawn with the cut in one colour and the travel dim, the table of layers (mode, power, speed, passes, step of the focus, width of the beam and its side, tabs, hatch angle and spacing) is edited in the window, a settings file can be loaded, the notes of the reading and of the plan are listed, the time is estimated and the G-code is exported with the same header as the one of a picture. The words are in the eight languages.
- **A window:** built with `--features gui`, `phoenix-laser` with no arguments (or with one picture, or `gui [IMAGE]`) opens a window in the look of the other programs of the suite (amber on charcoal, the icon of the program). A PNG or PGM picture is opened from the list of files of the window or dropped on it; the passes of the laser are drawn as the head makes them (burning in a colour that follows the power, travel and overscan thin), with zoom (wheel) and pan (drag); the width, the size of a dot, the dithering and its threshold, the feed, the power, the full power value, the overscan (typed or worked out from the acceleration) and the origin can be edited, a calibration grid of power against feed can be made, and the G-code is exported with the same header as the command line. The command line works as before, and a build without the feature is only a command line.
- **The window speaks the eight languages:** English, Spanish, German, French, Italian, Japanese, Chinese and Portuguese of Portugal, chosen from the system and changeable in the window.
- **The logic of the window needs no screen:** `window` (picture, settings, engraving, passes, export, status), `viewport` (zoom and pan), `browse` (the list of files) and `lang` (the words) are plain code with their own tests; `gui` only draws them.
- **The Rust version needed is 1.88,** the one the window needs.

- **Renamed:** The project is now called EH3D-PHOENIX-LASER (it was EH3D-LASER-CAM); it joins the PHOENIX family of programs.

## [0.0.3] - Audit fixes, the new reading limits, tests and the application icon

- **The application icon and the logos of the program:** `images/brand/` holds the icon (SVG, PNG sizes, `.ico` and `.icns`), the horizontal and vertical logos in a light and a dark version and the social preview image.
- **Shared checks updated:** the validator also compares the badge and the Version row of the README with the manifest, fails when one of its checks cannot run, and the CHANGELOG step of the workflow reads the base branch from the environment.
- **Every G-code file opens with a standard header:** comment lines with the generator and its version, the units (mm, G21), the picture it was made from with its SHA-256 and the tools (the laser and its power); the calibration grid says it has no source. The library functions keep returning the program alone, so the header belongs to the files the command line writes.
- **One way to write a number, and no `NaN` or `inf` in a file:** the engraving and the calibration grid write every number with the same function (`gcode_out::number`: three decimals at most, no `-0`), and a value that is not finite is an error. The SHA-256 used by the header is written in the program itself (no new dependency) and checked against the known test vectors.
- **The reader of pictures comes from EH3D-COMMON (`eh3d-image`):** the program no longer keeps its own copy of the PGM and PNG reader; it takes it by path from the sibling repository, which must be cloned beside this one. `eh3d_*::image` keeps working as before. The manifest names EH3D-COMMON in `depends_on` and the CI checks it out.
- **More tests:** the G-code read back into the dots it was made from, the limits of the head and of every value, the calibration grid square by square, and the command line with its errors and file names in any script.
- **The workflows are hardened:** every action is pinned by its commit with its version in a comment, and the checkouts keep no credentials.
- **More tests of the limits:** every value of the parameters at its edges, what the engraving reports, and the shape of the lines at the ends.

## [0.0.2] - Dry run for engraving

- **Strict command line:** an option that is written wrong (`--powr`) or a word too many is an error that names it; before, it was ignored and the output was made with the default values.
- **A dot size that makes no sense is refused before anything is reserved:** `--dot-mm 0` or a tiny one, or an image that would be larger than the limit, gives an error instead of an allocation failure or an overflow.

- **One shared helper for the command-line arguments** (`src/cli_args.rs`: flag, switch, num and a strict finish), the same file in every small utility of the suite; the copies this program had behaved the same, so nothing changes for a person.

## [0.0.1] - An image engraved by a laser: dithering, raster G-code with dynamic power and a calibration grid

- **The image:** PNG (grey, colour, transparent, 8 or 16 bits) and PGM, with the size limited; `resize` averages the pixels.
- **The dots:** threshold, Floyd-Steinberg and Atkinson, checked to keep the darkness of a grey.
- **The laser:** `M4` with `S0` while it travels, alternating directions, an overscan fixed or worked out from the acceleration, and the top of the image as the highest Y.
- **The calibration grid:** a square for every pair of a power and a feed.
- **The command line** `eh3d-lasercam` with `engrave`, `calibrate` and `info`, and a sample gradient.
- **18 tests** run on a computer, with damaged input.
